## Контракт результата (читай первым)

Твой ответ — вход машинного решения. Он **обязан** заканчиваться ровно одним блоком ```json с
объектом `{"verdict": ..., "findings": [...]}`: проза выше — для человека, блок — для
`cycle-decide`, и он читает только блок.

- Ограждение — три обратных кавычки и слово `json`, без меток и суффиксов;
- после блока — ничего: ни строки, ни второго блока;
- поля верхнего уровня — только `verdict` и `findings`.

Схема блока:

```json
{ "verdict": "merge-ready", "findings": [] }
```

`verdict` — `merge-ready` или `needs-changes`. Каждый элемент `findings`: `id` (строка), `severity`
(`BLOCKER`|`MAJOR`|`MINOR`|`FOLLOW-UP`), `file` (строка), `line` (целое ≥ 1), `summary` (строка),
`repro` (строка), `in_scope` (bool), `preexisting` (bool). У BLOCKER/MAJOR `file`, `line` и `repro`
обязательны. У MINOR/FOLLOW-UP они могут быть пустыми: `null` или `""`, но не `0`.

Ищи: реальные баги и граничные случаи, пропущенные тесты, утечки секретов и обход авторизации,
неидемпотентные операции, нарушения границ слоёв и обратной совместимости, нарушения `AGENTS.md`.

Правила качества:

- Каждое BLOCKER/MAJOR сопровождай сценарием воспроизведения (шаги → фактический результат). Нет
  сценария — максимум MINOR или FOLLOW-UP.
- У каждого замечания есть два признака: `in_scope` — лежит ли оно в скоупе плана, `preexisting` —
  существовало ли оно до диффа. Решает `cycle-decide`, не ты.
- На повторном ревью проверяй исправление прежних замечаний и новые изменения; закрытые замечания не
  повторяй и не расширяй скоуп новыми темами.
- Если замечаний нет — так и напиши, без выдуманных придирок.

**Финальный блок** — последнее в ответе, ровно один, пример:

```json
{
  "verdict": "needs-changes",
  "findings": [
    {
      "id": "B1",
      "severity": "BLOCKER",
      "file": "scripts/foo.mjs",
      "line": 42,
      "summary": "одна фраза: что не так",
      "repro": "шаги → фактический результат",
      "in_scope": true,
      "preexisting": false
    }
  ]
}
```
