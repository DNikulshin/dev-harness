# Как участвовать

Спасибо, что дошли до этого файла. Здесь — короткий вход: что делать с идеей, как оформить правку и
что проверить до PR. Полный норматив процесса — [`docs/workflow.md`](./docs/workflow.md), правила
разработки ядра — [`AGENTS.md`](./AGENTS.md); этот файл их не пересказывает, а только ведёт.

## Идея или дефект

Работа идёт по issues — без issue нет ветки и PR.

| Что у вас                                | Куда                                                                            | Метки                              |
| ---------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------- |
| Дефект с воспроизведением                | [issue по шаблону](https://github.com/DNikulshin/dev-harness/issues/new/choose) | `type:bug`, `area:*`, `prio:*`     |
| Новая возможность                        | то же                                                                           | `type:feature`, `area:*`, `prio:*` |
| Инфраструктура, зависимости, рефакторинг | то же                                                                           | `type:chore`, `area:*`, `prio:*`   |
| Вопрос по использованию                  | issue с `question`                                                              | —                                  |

Метки `status:todo|in-progress|review|blocked` двигают карточку на доске — их ставим руками или
автоматикой, но состояние задачи всегда можно проверить фактом: `gh issue view <номер>`.

**Об уязвимости — не через issue.** Порядок описан в [`SECURITY.md`](./SECURITY.md): публичный тред
с деталями вредит раньше, чем мы успеем выпустить исправление.

## Ветка

```bash
git switch main && git pull --ff-only
git switch -c feat/214-invoice-export  # или fix/, chore/, docs/
```

- префикс — по типу задачи: `feat/`, `fix/`, `chore/`, `docs/`;
- в имени — номер issue и короткий латинский slug: `fix/179-pr-reference-inline-code`;
- ветка создаётся от актуального `main`: устаревшая база даёт конфликт и **не запускает проверки
  вообще** — PR приезжает `CONFLICTING`, а CI молчит.

## Коммит

`<type>(<scope>): <что сделано>` — одна строка про суть, детали в теле: почему так, что отвергли.

- один коммит — одно логическое изменение;
- ссылка на issue — в теле PR (`Closes #42`), не в коммите;
- **closing-слово (`closes`/`fixes`/`resolves` + номер) в сообщении коммита тоже закрывает issue** —
  GitHub разметку там не разбирает. Пример с чужим номером в тексте коммита закроет чужую задачу.

## Проверки перед PR

```bash
corepack enable            # pnpm из packageManager
pnpm install
node --version             # 26.13 или новее: engines.node = >=26.13, версия из .nvmrc
pnpm check                 # node --test + tsc --noEmit + prettier --check
```

- `pnpm check` — обязательный минимум: тесты, строгая типизация JS+JSDoc, форматирование.
- Новое поведение — с тестом (`node:test`); правка документации — без тестов, но с проверкой, что
  ссылки в файле живые (`pnpm issue-refs` для ссылок на issues).
- Секретов в диагностике и тестовых данных нет: правило — `AGENTS.md`, п. 4 и 7.

## Границы правки

| Не трогаем                                 | Почему                                                                       |
| ------------------------------------------ | ---------------------------------------------------------------------------- |
| `types/`                                   | генерируется `pnpm typecheck:types` — правка разъедется при следующей сборке |
| `pnpm-lock.yaml`                           | только осознанное изменение зависимостей, отдельным коммитом                 |
| `.pi/artifacts/`, `node_modules/`          | артефакты циклов и установленные пакеты, не исходники                        |
| нормативные тексты `docs/orchestrator*.md` | изменение протокола — через issue и ADR, а не походя                         |

Новая зависимость — только с обоснованием в PR: у ядра нет runtime-зависимостей, и это свойство, а
не случайность. Названия проектов, пакетов и каталогов приложений в ядро не попадают: всё проектное
живёт в `.pi/harness.config.json` и `AGENTS.md` потребителя.

## PR

- заголовок — как у коммита; тело: что сделано, почему так, как проверять, `Closes #N`;
- чек-лист шаблона PR заполняется по факту, а не «галочками»;
- обязательные проверки: `checks (ubuntu-latest)`, `checks (macos-latest)`, `pr-references`,
  `issue-refs`, `labels`;
- мерж в `main` — squash; делает владелец репозитория. Агент или участник доводит PR до зелёного CI.

## Правила поведения

Участие в проекте регулируется [`CODE_OF_CONDUCT.md`](./CODE_OF_CONDUCT.md) (Contributor Covenant
2.1). Нарушения — тому же адресату, что и вопросы по поведению: приватно, без публичного треда.

## Лицензия правки

Отправляя PR, вы соглашаетесь, что правка распространяется под MIT (см. [`LICENSE`](./LICENSE)):
код, скрипты, шаблоны и документация — одна лицензия, правообладатель общий.
