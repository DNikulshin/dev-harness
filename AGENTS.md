# AGENTS.md — dev-harness

## Что это

`dev-harness` — переиспользуемое ядро цикла разработки: детерминированные скрипты
`plan → code → gates → review → evaluate → decide`, схема артефактов, проверка раскладки harness и
evals-слой. Проекты подключают репозиторий как git-зависимость и задают свои гейты, лимиты и пути в
`.pi/harness.config.json`.

Ядро не знает конкретный проект: в коде, тестах и фикстурах не должно быть названий проектов, их
пакетов, каталогов приложений и провайдеров моделей. Всё проектное — в конфиге и `AGENTS.md`
потребителя.

## Структура

| Путь                 | Что там                                                               |
| -------------------- | --------------------------------------------------------------------- |
| `scripts/`           | CLI ядра: `cycle-*.mjs`, `check-harness.mjs`, `evals-*.mjs`           |
| `scripts/lib/cycle/` | общие модули ядра: конфиг, пути, git, io, redaction, refs, валидаторы |
| `scripts/lib/evals/` | evals-слой: цены, профили, сиды, скоринг                              |
| `scripts/fixtures/`  | фикстуры тестов, включая фикстурный конфиг проекта                    |
| `templates/.pi/`     | шаблоны для потребителя: роли агентов, промпт цикла, пример конфига   |
| `docs/`              | норматив протокола, vision, история выноса                            |
| `evals/`             | снапшоты цен, профили нагрузки, сиды синтетических диффов             |

## Команды

| Команда             | Что делает                          |
| ------------------- | ----------------------------------- |
| `node --test`       | все тесты репозитория               |
| `pnpm format:check` | проверка форматирования (prettier)  |
| `pnpm format`       | форматирование                      |
| `pnpm check`        | `node --test && prettier --check .` |

Проверки проекта-потребителя задаются в его `.pi/harness.config.json` (секция `gates`) и описываются
в его `AGENTS.md`; ядро эти команды не знает.

## Правила

1. **Никаких проектных строк в ядре.** Названия проектов, пакетов, каталогов приложений, провайдеров
   моделей — только в конфиге и документации потребителя. Нейтральные примеры: `acme`,
   `example.com`, `@acme/core`, `apps/service`; префикс провайдера моделей — только в конфиге.
2. **Гейты, лимиты и пути — из `.pi/harness.config.json`.** Зашитые в код гейты запрещены. Пустой
   список гейтов — валидное состояние: `cycle-gates` сообщает «гейты не заданы» (код 2).
3. **Конфиг строгий.** Неизвестная секция/поле, неверный тип, отрицательное число, пустой `id`,
   дубли `id`, отсутствующий `executable` — ошибка с кодом 2, без молчаливого дефолта.
4. **Секреты не печатаем.** Диагностика не содержит содержимого `.env*` и тел файлов.
5. **ESM, plain Node.** Новые зависимости — только с обоснованием; тесты — `node:test`.
6. **Не коммить и не пушить** без явного указания владельца.
7. **Фикстуры — вымышленные.** Телефоны, пароли и имена в тестовых данных не должны быть похожи на
   настоящие; строки подключения к БД не копируются из проектов.

## Норматив протокола

`docs/protocol.md` — точка входа. Нормативные документы: `docs/orchestrator-core.md` (реализация,
Приложения A–D) и `docs/orchestrator.md` (политика). Проектные значения (гейты, лимиты, пути)
подставляются из `.pi/harness.config.json` проекта.
