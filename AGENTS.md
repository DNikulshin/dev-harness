# AGENTS.md — dev-harness

## Что это

`dev-harness` — переиспользуемое ядро цикла разработки: детерминированные скрипты
`plan → code → gates → review → evaluate → decide`, схема артефактов, проверка раскладки harness и
evals-слой. Проекты подключают репозиторий как git-зависимость и задают свои гейты, лимиты и пути в
`.pi/harness.config.json`.

Ядро не знает конкретный проект: в коде, тестах и фикстурах не должно быть названий проектов, их
пакетов, каталогов приложений и провайдеров моделей. Всё проектное — в конфиге и `AGENTS.md`
потребителя.

## Структура

| Путь                 | Что там                                                               |
| -------------------- | --------------------------------------------------------------------- |
| `scripts/`           | CLI ядра: `cycle-*.mjs`, `check-harness.mjs`, `evals-*.mjs`           |
| `scripts/lib/cycle/` | общие модули ядра: конфиг, пути, git, io, redaction, refs, валидаторы |
| `scripts/lib/evals/` | evals-слой: цены, профили, сиды, скоринг                              |
| `scripts/fixtures/`  | фикстуры тестов, включая фикстурный конфиг проекта                    |
| `templates/.pi/`     | шаблоны для потребителя: роли агентов, промпт цикла, пример конфига   |
| `docs/`              | норматив протокола, процесс, доска, vision, история выноса            |
| `evals/`             | снапшоты цен, профили нагрузки, сиды синтетических диффов             |

## Команды

| Команда                | Что делает                                            |
| ---------------------- | ----------------------------------------------------- |
| `node --test`          | все тесты репозитория                                 |
| `pnpm typecheck`       | `tsc --noEmit`: строгая проверка типов (JS + JSDoc)   |
| `pnpm typecheck:types` | пересобрать `types/` — `.d.ts` для потребителя пакета |
| `pnpm rag:sync`        | синхронизировать индекс `local-rag` по `docs/`        |
| `pnpm board:sync`      | сверить доску Projects с issues (`docs/board.md`)     |
| `pnpm board:sync:dry`  | показать план сверки, ничего не записывая             |
| `pnpm git:hygiene`     | ветки со смерженными PR, статус текущей ветки         |
| `pnpm precommit`       | хук вручную: ветка, prettier, check-harness           |
| `pnpm format:check`    | проверка форматирования (prettier)                    |
| `pnpm format`          | форматирование                                        |
| `pnpm check`           | `node --test && tsc --noEmit && prettier --check .`   |

Проверки проекта-потребителя задаются в его `.pi/harness.config.json` (секция `gates`) и описываются
в его `AGENTS.md`; ядро эти команды не знает.

## Правила

1. **Никаких проектных строк в ядре.** Названия проектов, пакетов, каталогов приложений, провайдеров
   моделей — только в конфиге и документации потребителя. Нейтральные примеры: `acme`,
   `example.com`, `@acme/core`, `apps/service`; префикс провайдера моделей в коде ядра (`scripts/`)
   не встречается — он приходит из `.pi/harness.config.json`. Исключение — поставляемые
   `templates/.pi/agents/*.md` и собственный `.pi/` этого репозитория: в них стоит реальный префикс
   провайдера, тот же, что в `.pi/harness.config.json`, иначе потребитель, скопировавший шаблоны
   вместе с примером конфига, получает провал H4 «model не начинается с провайдера».
2. **Гейты, лимиты и пути — из `.pi/harness.config.json`.** Зашитые в код гейты запрещены. Пустой
   список гейтов — валидное состояние: `cycle-gates` сообщает «гейты не заданы» (код 2).
3. **Конфиг строгий.** Неизвестная секция/поле, неверный тип, отрицательное число, пустой `id`,
   дубли `id`, отсутствующий `executable` — ошибка с кодом 2, без молчаливого дефолта.
4. **Секреты не печатаем.** Диагностика не содержит содержимого `.env*` и тел файлов.
5. **ESM, plain Node.** Новые зависимости — только с обоснованием; тесты — `node:test`.
6. **Коммит и push — только в рабочую ветку задачи.** Прямой коммит/push в `main` запрещён; правило
   проверяется хуками `pre-commit`/`pre-push`, а не памятью. PR открывает агент, проверяет и мержит
   — владелец. Подробности — `docs/workflow.md`.
7. **Фикстуры — вымышленные.** Телефоны, пароли и имена в тестовых данных не должны быть похожи на
   настоящие; строки подключения к БД не копируются из проектов.

## Git, issues, Kanban

- Работа идёт по issues: каждая задача — issue с метками `type:*`, `area:*`, `prio:*`. Статусы
  (колонки доски) — метки `status:todo|in-progress|review|blocked`.
- Ветки: `feat/*`, `fix/*`, `chore/*` от `main`, имя содержит номер issue.
- Merge в `main` делает только владелец, squash: история линейная. Прямой push в `main`, force-push
  и удаление `main` запрещены и для владельца (`enforce_admins`), правила ветки ставятся
  `node tooling/gh-setup.mjs --protect`.
- Состояние задачи берётся фактом: `gh issue view <номер>`, `gh pr list --head <ветка>`,
  `pnpm git:hygiene` перед началом работы и перед докладом о статусе.
- Коммиты: `<type>(<scope>): <что сделано>`, один коммит — одно логическое изменение.
- Инструмент GitHub — только `gh` CLI (GitHub MCP не подключаем).

Полный процесс — `docs/workflow.md`: роли, ветки, коммиты, PR, релизы, Definition of Done. Доска
Projects — `docs/board.md`.

## Границы действий агента

- Коммитить и пушить можно только в рабочую ветку по текущей задаче. Хуки `pre-commit`/`pre-push`
  отклоняют запись в `main`/`master` локально, `enforce_admins` — на GitHub.
- Правки минимальные, в рамках задачи; без попутного рефакторинга и переименований.
- Новая зависимость — только с обоснованием в ответе.
- Не трогать: `node_modules/`, `types/` (генерируются `pnpm typecheck:types`), `pnpm-lock.yaml`
  (кроме осознанного изменения зависимостей), `.pi/artifacts/`.

## Норматив протокола

`docs/protocol.md` — точка входа. Нормативные документы: `docs/orchestrator-core.md` (реализация,
Приложения A–D) и `docs/orchestrator.md` (политика). Проектные значения (гейты, лимиты, пути)
подставляются из `.pi/harness.config.json` проекта.

## Актуальный контекст через local-rag

Индекс `docs/` синхронизируется в начале **и** в конце сессии: знания о документах стареют молча, а
решения принимаются по актуальным файлам. Полное правило — `docs/rag.md`; здесь короткая версия.

1. В начале сессии: `local-rag_sync_start` только для `<корень>/docs`, дождаться
   `local-rag_sync_status`. Индексируется только `docs/` — не весь репозиторий и не
   `/home/dev/projects/`: база общая, синк корня одного проекта перетирает чужие документы.
2. Запросы — со `scope=<корень>` и по существу задачи. Результаты — навигация к источникам:
   `AGENTS.md`, код и файлы `docs/` остаются истиной.
3. RAG недоступен — fallback без блокировки: читать `docs/` напрямую (`grep`, `find_files`, `read`),
   выполнить задачу и явно сказать, что сработал fallback и почему.
4. В конце сессии: повторить синк по `docs/` и проверить статус. Не выполнен — сказать об этом в
   итоге.
5. В RAG не отправляются `.env*`, пользовательские данные, `node_modules`, generated-файлы,
   `.pi/artifacts/`.

Автоматизация после мержа: `.githooks/post-merge` → `pnpm rag:sync` (`tooling/rag-sync.mjs`). Скрипт
— инфраструктура среды, в пакет не входит и потребителю не поставляется (ADR 0003): потребитель
получает правило `docs/rag.md`, а не копию скрипта. Включение хуков в клоне:
`git config core.hooksPath .githooks` (настройка локальная, в репозитории не передаётся).
