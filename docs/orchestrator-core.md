## 4. Инварианты реализации

- **Стиль:** ESM `.mjs`, shebang, JSDoc с типами, комментарии на русском, `execFileSync`/
  `spawn` без оболочки (как в `scripts/precommit.mjs`), корень репозитория через
  `git rev-parse --show-toplevel`. Скрипты линтятся (`eslint scripts`) и форматируются prettier.
- **Без зависимостей:** только `node:*`. Сеть не используется; `gh` вызывает супервизор,
  скрипты читают его вывод из файла.
- **Детерминизм:** вывод JSON с упорядоченными ключами и массивами; время и случайность
  внедряются параметром (в тестах фиксируются); запись файлов атомарная (tmp + rename).
- **Права:** скрипты пишут только в `.pi/artifacts/<…>/` (и lock-файл), не читают `.env*`,
  не меняют код, не запускают деструктивных команд. Исключение: `git add --intent-to-add`
  для untracked-файлов (индекс меняется, содержимое нет).
- **Коды выхода:** `0` — успех; `1` — штатное отрицательное (упал обязательный гейт);
  `2` — ошибка использования или внутренняя; `3` — конфликт состояния (блокировка,
  недопустимый переход); `4` — превышение лимита (`diff_too_large`). Результат всегда
  пишется и в stdout (одна строка JSON), и в файл.
- **ПДн:** в тестах и фикстурах только вымышленные данные. Маскирование — §5.4.
- **Безопасность:** файлы `.pi/artifacts/` не коммитятся и не индексируются RAG (уже так).
- **Изменения вне перечня файлов §5.1 в этой поставке запрещены.**

**Где искать конфиг (ADR 0005, б).** Единственная фиксированная точка раскладки — путь к конфигу.
По умолчанию это `<root>/.pi/harness.config.json`; другой путь задаётся флагом `--config <file>` или
переменной окружения `HARNESS_CONFIG`, флаг важнее переменной. Флаг забирает из `argv` граница CLI —
`takeConfigOption` в `config.mjs`, поэтому остальные парсеры аргументов о нём не знают, а `--config`
означает одно и то же у всех `bin`, читающих конфиг. Относительный путь считается от корня проекта,
как и все остальные пути ядра. Явно заданный путь, которого нет на диске, — ошибка с кодом 2, а не
молчаливые дефолты: иначе опечатка выглядит как «настройки применились». Всё остальное берётся из
секций конфига, а сообщения об ошибках называют фактический путь (`config.configFile`): ошибка в
`harness/harness.config.json` не должна отправлять читателя в `.pi/`.

**Источники лимитов (#235).** Шесть лимитов — `maxCycleCostRub`, `defaultMaxIterations`,
`maxDiffLines`, `maxDiffBytes`, `logMaxBytes`, `evidenceTailLines` — читаются из проектного
конфига `.pi/harness.config.json` (раздел `limits`), который разбирает `config.mjs`, а поверх
работают переопределения из `lib/cycle/limits.mjs`. Приоритет по каждому ключу: CLI-флаг
(`--max-cost-rub` у `cycle-decide`, `--max-iterations` у `cycle-state init`) → переменная
окружения `HARNESS_LIMIT_<КЛЮЧ_В_SNAKE_UPPER>` → конфиг проекта → дефолт в `config.mjs`.
Невалидное значение (не число, не целое где нужно, вне диапазона, неизвестный ключ, битый JSON) —
ошибка с кодом 2, а не молчаливый откат к дефолту. Применённые значения и их источник видны
в `decision.<n>.json` (`applied_limits`) и `metrics.json` (`applied_limits`), а источник порога
бюджета — в тексте причины `budget: … (правило 7 §5.6, лимит: …)`.

**Правила целостности проверок (#27).** Секция `integrity` в `.pi/harness.config.json` отвечает
на вопрос «что в этом проекте считается проверкой»: `testPaths` — файлы тестов, `protectedPaths` —
файлы, которые агент не должен править молча (конфиг гейтов, `.pi/agents/*`, `AGENTS.md` — список
задаёт проект). Каждое правило — относительный путь или glob: `*` — в пределах сегмента,
`**` — через сегменты, `?` не поддерживается; правило без wildcard задевает и всё вложенное, как
префиксы `qaWeb.pathPrefixes`. Запрещены абсолютные пути, `..`, `.` и пустые сегменты — ошибка
с кодом 2, а не молчаливое правило, которое никуда не попадает. Пустая секция (и её отсутствие) —
валидное состояние: контролю нечего проверять, артефакт не пишется. Умолчаний с готовым списком
путей ядро не держит: тесты и защищённые файлы — свойство проекта, а не догадка ядра.

**Ветка цикла (#274).** `init` фиксирует имя ветки только в `state.json` и git не трогает, поэтому
перед записью состояния проверяется, что ветка существует и `HEAD` на ней: иначе коммиты и
`gh pr create` уходили бы не туда, а рассинхрон всплывал бы только на PR-стадии. Та же сверка
выполняется в `advance --to PR` и в `apply-decision`, если решение открывает `PR` (`PROCEED*`).
Проверка ничего не мутирует: ветку создаёт человек или агент, CLI только отказывается работать
в чужой ветке и печатает готовую команду `git switch`.

### 5.3 `cycle-state.mjs`

Единственный писатель `state.json`. Подкоманды:

```
init     --issue N --slug S --branch B [--date YYYY-MM-DD] [--max-iterations 2] [--dir D]
get      [--dir D] [--field F]
advance  --to STAGE [--dir D] [--owner-approved]   --to PR и выход из ESCALATED сверяют ветку
finish   --stage STAGE --status done|error [--detail T] [--dir D]
freeze-criteria [--dir D] [--owner-approved]  закрепляет дайджест критериев из issue.json
apply-decision [--dir D]              применяет decision.<n>.json
escalate --reason R [--detail T] [--dir D]   пишет escalation.json, ставит ESCALATED
resume   [--dir D]                    печатает первый незавершённый этап
lock [--dir D] [--slug S] | unlock [--dir D]  блокировка дерева, см. ниже
```

`finish --detail T` и `escalate` (туда попадает причина эскалации) пишут `detail` в
закрываемую запись `history[]`; поле необязательное, формат — Приложение A.

**Конфликты записи (#33).** Все мутации идут по протоколу «прочитал → проверил → записал»:
команда передаёт в `writeState` снимок `state.json` (разобранное состояние плюс текст файла), и
перед записью текст на диске сверяется побайтно со снимком. Расхождение — код 3 с причиной
`state_conflict`, файл остаётся нетронутым, а команду нужно повторить: она перечитает состояние.
Так закрыты оба сценария last-write-wins — потерянная заморозка критериев и откат `stage`/
`history` к снимку до перехода. `init` передаёт `null`-снимок («файла ещё нет»), поэтому гонка
двух `init` тоже видна. Это обнаружение, а не блокировка: между сверкой и `rename` окно
остаётся, мьютекса на файловой системе нет (распределённая блокировка — вне задачи).
Побайтное сравнение ловит и правку человеком, включая изменение одного форматирования: любой
чужой текст — повод отказать, а не угадывать, менялось ли поле.

**Каталог цикла (`--dir`).** Явный `--dir` — путь как есть. По умолчанию `init` собирает
`<artifacts>/<date>-<issue>-<slug>`, а `get`/`advance`/`finish`/`apply-decision`/`escalate`/
`resume` берут единственный активный цикл (`findActiveCycle`): подкаталог со `state.json`,
у которого `stage` ∉ {`DONE`, `ESCALATED`}. Активных ноль или больше одного — код 2:
неоднозначность должна ломать цикл, а не разрешаться угадыванием. Поэтому `get` для
терминального цикла (`DONE`/`ESCALATED`) требует явного `--dir` — по умолчанию такой каталог
не виден; `resume` в терминальном цикле завершается кодом 3, как и любая мутация: после
`DONE`/`ESCALATED` читается только `get`. `lock`/`unlock` от `findActiveCycle` не зависят:
их каталог — `.pi/artifacts/` (или `dirname(--dir)`, если он задан), поэтому `unlock`
работает и после `DONE`/`ESCALATED`.

Допустимые переходы (всё остальное → код 3). В `ESCALATED` ведёт только `escalate`
(и `apply-decision` с `ESCALATE`): `advance --to ESCALATED` отклоняется — у эскалации свои
защиты и `escalation.json`. Эскалация с `QA_WEB` нужна, например, для `diff_too_large`,
обнаруженного на ANALYSIS уже после браузерной проверки: `escalate` закрывает открытую
запись этапа `error` (отдельный `finish` не требуется) и считает `draft_pr_allowed` по
общим правилам ниже.

| Из               | В                                                         |
| ---------------- | --------------------------------------------------------- |
| INIT             | PLAN, ESCALATED                                           |
| PLAN             | CODE, ESCALATED                                           |
| CODE             | GATES                                                     |
| GATES            | QA_WEB, REVIEW, ESCALATED                                 |
| QA_WEB           | REVIEW, ESCALATED                                         |
| REVIEW           | EVALUATE, DECIDE                                          |
| EVALUATE         | REVIEW, DECIDE                                            |
| DECIDE           | REWORK, ACQUIRE_EVIDENCE, REVIEW, EVALUATE, PR, ESCALATED |
| REWORK           | CODE                                                      |
| ACQUIRE_EVIDENCE | GATES, QA_WEB, REVIEW                                     |
| PR               | DONE                                                      |

**`ACQUIRE_EVIDENCE → REVIEW`** реализовано в #47: `acquire: integrity` (§5.6) означает повтор
ревью с вопросом «не ослаблены ли проверки», а не гейт и не браузерную проверку — без этого
ребра добор целостности упирался в тупик: из `ACQUIRE_EVIDENCE` вели только `GATES` и `QA_WEB`.
Драйвер маршрутизации выбирает эту цель по `acquire[]` решения, а не по смыслу.

**`QA_WEB → ESCALATED`** реализовано (issue #202): ребро есть в `TRANSITIONS.QA_WEB`, его
требует Приложение B (`escalate --reason diff_too_large` на ANALYSIS уже после QA_WEB).
`advance --to ESCALATED` при этом остаётся запрещён на любом этапе.

**`ESCALATED → DECIDE`** (#235) — единственное обратное ребро из терминального этапа: владелец
поднимает бюджет и цикл досчитывает решение в том же каталоге, вместо ручного оформления PR.
Разрешено только `advance --to DECIDE --owner-approved`; эскалация снимается (`escalation: null`),
`iteration` и `history` сохраняются, запись `DECIDE` открывается заново (`stage_status: running`).
Любая другая цель из `ESCALATED` — код 3, и `DONE` остаётся терминальным без исключений.

Защиты:

- `REWORK → CODE` увеличивает `iteration` — это единственное место инкремента в автомате;
  при `iteration ≥ max_iterations` переход недопустим без `--owner-approved` (флаг пишется в
  `state.json` и переживает перезапуски). `apply-decision` с `REWORK` счётчики не меняет:
  иначе первый же `REWORK` упирался бы в лимит, а `iteration > max_iterations` без
  `owner_approved` не проходит схему состояния;
- `→ DECIDE` только если для текущей итерации есть `review.<n>.md` и `evaluation.<n>.md`;
- `→ PR` только если последнее `decision` имеет `action` `PROCEED` или `PROCEED_WITH_UNVERIFIED`;
- `apply-decision` идемпотентен: `RETRY_STAGE` → `retries[stage]++` и переход в этот этап;
  `ACQUIRE_EVIDENCE` → `retries.evidence++`; `REWORK` → только переход в `REWORK` (инкремент —
  на ребре `REWORK → CODE`, п. 1); `ESCALATE` → `escalate`; `PROCEED*` → `PR`. Повторный
  запуск с тем же решением — no-op с кодом 0 (файл не перезаписывается): сравнивается
  записанный маркер `applied_decision` (`iteration`, `action`, `retry_stage`, `digest`
  содержимого решения), поэтому счётчики не растут дважды. Изменённое решение применяется по
  общим правилам, а когда переход уже невозможен (не `DECIDE`, терминальный этап) — код 3,
  а не молчаливый успех;
- `freeze-criteria` закрепляет цель итерации: в `state.json` пишется `criteria_sha256` —
  `sha256` пар `[id, формулировка]` критериев, **извлечённых из `issue.json`** тем же разбором,
  что в `cycle-evidence` (`lib/cycle/criteria.mjs`). Источник — issue, а не `evidence/criteria.md`:
  файл производный, и закреплять его значило бы разрешить подменить цель до первой заморозки.
  Повторный прогон с теми же критериями — no-op (код 0, файл не перезаписывается), изменённые
  критерии — код 3 `criteria_drift`, пока их не подтвердит владелец флагом `--owner-approved`
  (подтверждение фиксируется в `state.owner_approved`). Нет `issue.json` или критериев в нём —
  код 2: закреплять нечего. Терминальный этап — код 3, как у любой мутации;
- `escalate` вычисляет `draft_pr_allowed` (§9): проход `code` завершён и обязательные гейты
  зелёные, то есть `gates.<n>.json` текущей итерации валиден, содержит ≥ 1 гейт
  `required: true`, и каждый обязательный гейт — `pass` или `not_run` с причиной
  `no_database`; причина ∈ {`iteration_limit`, `budget`, `agent_output_invalid`}. Проверка
  fail-safe: нет файла, битый документ, чужая итерация, пустой список гейтов, обязательный
  `fail`, `skipped` или `not_run` по другой причине → `false` (неполные данные — не повод
  открывать draft PR).

**Блокировка (`lock`/`unlock`).** Файл `.pi/artifacts/.lock` = `{ pid, slug|null, created_at }`.
В `pid` пишется **родительский** процесс (`ppid`) — супервизор, который ведёт цикл: сам
`cycle-state` живёт миллисекунды и блокировку держать не может; если родителя нет (`ppid`
0/1), берётся собственный pid. Захват атомарный (эксклюзивное создание файла), поэтому два
параллельных `lock` в одном дереве не могут оба получить код 0. Занятый lock: живой pid —
код 3. Пустой файл моложе 30 с — идущий прямо сейчас захват (тоже код 3); старше — сбой
между созданием и записью, такой файл восстанавливается автоматически, иначе дерево
заклинило бы до ручного `unlock`. Мёртвый, битый или заброшенный lock снимается, но
восстановление сериализовано файлом `<lock>.takeover` с TTL 30 с: без него два процесса
снимали бы lock по очереди и второй снёс бы уже свежую блокировку первого. Под
сериализатором состояние перепроверяется, а снятие идёт через переименование со сверкой
inode — удаления «по пути» нет. `unlock` безусловен: отсутствующий файл — no-op с кодом 0;
вызывается и на `DONE`, и на `ESCALATE` (иначе lock с живым pid супервизора держит дерево до
конца сессии).

### 5.3a `cycle-driver.mjs`

```
node scripts/cycle-driver.mjs next [--dir D] [--root R]       что делать прямо сейчас
node scripts/cycle-driver.mjs run  [--dir D] [--max-steps N]  исполнить детерминированные шаги
```

Маршрутизация стадий кодом вместо LLM-супервизора (issue #47, «фаза 3» §17
`docs/orchestrator.md`). Драйвер читает `state.json`, наличие артефактов и `decision.<n>.json`
и отвечает одним дескриптором шага: `action` (`run` / `advance` / `finish` / `spawn` /
`handoff` / `stop` / `blocked`), `step` (токен детерминированного скрипта), `reason`,
`commands` (готовые команды с путями), `waiting_for`, `allowed_next`. Решение принимает чистая
функция `lib/cycle/driver.mjs`; CLI только рендерит команды и исполняет их.

- `next` — только чтение состояния: не меняет `state.json` и артефакты, не запускает процессов
  и не зовёт моделей. Единственный побочный эффект — запись в журнал `driver.jsonl` (ниже).
- `run` — исполняет `run`/`advance`/`finish` подряд до первого `spawn`/`handoff`/`stop`/
  `blocked`. Работу моделей (`plan`, `code`, `review`, `evaluate`) и коммиты с PR драйвер не
  делает: он говорит, кому и с каким входом их передать.
- Писатель состояния остаётся один: драйвер зовёт `cycle-state` подпроцессом, а не правит
  `state.json` сам. Таблица переходов берётся из `TRANSITIONS`/`advanceTargets` — копии
  автомата в драйвере нет.
- Маршрутизация после закрытой стадии — факт, а не суждение: `GATES → QA_WEB` только при
  web-диффе от `base_sha`, `ACQUIRE_EVIDENCE` → цель из `acquire[]` решения, `REVIEW →
  EVALUATE → DECIDE` по протоколу.
- Коды выхода: `0` — шаг определён или исполнен; `1` — `blocked` (стадия закрыта с ошибкой,
  нет перехода, неизвестная стадия); `2` — ошибка использования или данных; `3`/`4` — коды
  подпроцесса (`state_conflict`, `diff_too_large`) без переупаковки.

**Журнал и наблюдаемость (#47).** Каждое отличающееся от предыдущего решение драйвер дописывает
строкой JSONL в `driver.jsonl` каталога цикла: `at`, `stage`, `status`, `action`, `step`,
`target`, `reason`, `executed`, `mismatch`. Повторный `next` на том же дереве ответа не меняет и
журнал не растит — счётчики считают шаги маршрута, а не число вопросов. Журнал — телеметрия, а
не артефакт протокола: в `evidence/` он не входит, руками не правится, при разборе цикла его
можно удалить (тогда `metrics.json` напишет блок `driver` как отсутствующий).

`mismatch` — расхождение состояния с предыдущим ответом драйвера: `true`, если после шага
состояние пришло не туда, куда шаг вёл (`advance` — в `target`, `finish`/`spawn`/`run` — в ту же
стадию). У `handoff` ожидание шире: работа передана супервизору (коммиты, PR, бриф, браузер) и
заканчивается его `finish` + `advance`, поэтому допустимы и цели `advanceTargets` — `PR → DONE`
после создания PR расхождением не считается. Не сверяются `apply-decision` (стадию переводит
решение, а не драйвер), `stop`/`blocked` и переход в `ESCALATED`: эскалация — штатный выход
протокола §18, а не обход маршрута. Ноль в `driver.mismatch` и есть измерение §17: маршрутизация
действительно кодом.

Граница объёма: драйвер не заменяет модели и не отменяет супервизора — он отбирает у него
решение «какая стадия следующая». Поведение супервизора описано в Приложении B; драйвер —
исполняемая форма той же таблицы.

### 5.4 `cycle-evidence.mjs`

```
criteria --dir D --issue-json F                 извлекает критерии (INIT)
packet   --dir D [--base SHA]                   собирает evidence/ для оценщика
```

**Критерии.** Вход — `gh issue view N --json title,body,labels` (файл готовит супервизор).
Тело разбирается как форма GitHub: секции `### <заголовок>`. Берётся секция
`Критерии приёмки` (шаблон feature) или `Готово, когда` (шаблон task); поле, равное
`_No response_`, считается пустым. Пункты — элементы списка (`- `, `* `, `1.`, `- [ ]`) →
`C1…Cn`, формулировка дословно. Нет секции, она пустая или в ней нет элементов списка →
код 2, причина `criteria_missing`. Для шаблона `bug.yml` отдельного поля критериев нет:
берётся секция `Ожидаемый результат` (элементы списка, а при их отсутствии весь текст секции
как единственный критерий `C1`).
Результат: `evidence/issue.md` и `evidence/criteria.md`.

**Пакет.** Перед диффом выполняется `intentToAddUntracked()`; дифф берётся от `base_sha`
(рабочее дерево против базы). Превышение лимита → код 4, `diff_too_large`. Копируются
`gates.<n>.json` и хвосты (до 200 строк) логов упавших гейтов; `qa-web.json`.

**Целостность проверок (#27).** Если секция `integrity` задаёт хотя бы одно правило, пакет
дополняется `evidence/integrity.json`: правила, с которыми считали (`test_paths`,
`protected_paths`), и затронутые диффом файлы по трём статусам — `added`, `modified`,
`deleted` — раздельно для `tests` и `protected`. Список берётся из `changedFilesWithStatus`
от той же базы, что и `diff.patch`, и сортируется: повторный прогон даёт побайтно тот же
файл. Тел файлов в артефакте нет — только пути. Правил нет — файла нет; чистый дифф при
заданных правилах даёт пустые списки, то есть явное «правок нет». Переименование
разворачивается в удаление и добавление (`--no-renames`), иначе переименованный тест выглядел
бы нетронутым файлом. Артефакт — факт, а не приговор: ядро не решает, ослаблены ли проверки,
оно делает правку видимой оценщику, ревью и владельцу.

**Маскирование** (копии логов в `evidence/` и сырые данные QA; сами логи гейтов уже
маскированы при захвате — §5.5, здесь маскируется то, что попадает в артефакт; в дифф
вносятся только секреты, строки не удаляются, номера строк сохраняются):

| Что                                                    | Замена                   |
| ------------------------------------------------------ | ------------------------ |
| e-mail                                                 | `[email]`                |
| телефон (форматы `+7`, `8`, общий `\+\d…`)             | `[phone]`                |
| значения после `authorization`, `cookie`, `set-cookie` | `[secret]`               |
| JWT (`eyJ….….…`)                                       | `[secret]`               |
| `postgres(ql)://user:pass@`                            | `postgresql://[secret]@` |
| значение после `key                                    | token                    | secret | password | passwd | pwd` (`=`или`:`, ≥8 символов) | `[secret]` |

Тесты обязаны проверять, что хэши коммитов, UUID и номера строк не маскируются.

### 5.5 `cycle-gates.mjs`

```
node scripts/cycle-gates.mjs --dir D [--only id,id] [--base SHA]
```

Гейты выполняются последовательно в порядке таблицы; зависимости: если гейт-родитель в
статусе `fail`/`not_run`, зависимый получает `not_run`, причина `blocked_by:<id>`. Остальные
гейты выполняются независимо (полнота картины для доработки). Вывод и ошибки — в
`gates/<id>.<n>.log` (при превышении 5 МБ сохраняется хвост). **Вывод маскируется при
захвате**: `redactLog` применяется к потоку stdout/stderr до записи, поэтому значения из
таблицы §5.4 не оказываются в файле лога даже на время — копия в `evidence/` маскируется
не вместо этого, а поверх. Строки буферизуются до перевода строки: секрет, разрезанный
между кусками pipe, всё равно распознаётся, а нумерация строк сохраняется. Тайм-аут
завершает процесс и его потомков: `fail`, причина `timeout`.

Состав, команды и условия запуска гейтов — **свойство проекта**: ядро берёт их из
`.pi/harness.config.json` (`gates[]`: `id`, `executable` + `args`, `required`, `dependsOn`,
`pathPrefixes`, `dbGate`). Таблица ниже — пример заполнения из проекта-источника; в другом
проекте `id`, команды, префиксы путей и зависимости задаются в его конфиге, а `no_database`
включается флагом `dbGate: true` у соответствующего гейта, а не по имени `test_int`.

| id                | Команда (пример: проект-источник)         | required | Зависит           | Условие запуска                                                                            |
| ----------------- | ----------------------------------------- | -------- | ----------------- | ------------------------------------------------------------------------------------------ |
| `contracts_build` | `pnpm --filter @acme/core build`          | да       | —                 | всегда                                                                                     |
| `typecheck`       | `pnpm typecheck`                          | да       | `contracts_build` | всегда                                                                                     |
| `lint`            | `pnpm lint`                               | да       | —                 | всегда                                                                                     |
| `check_arch`      | `pnpm check:arch`                         | да       | —                 | всегда                                                                                     |
| `lint_workflows`  | `pnpm lint:workflows`                     | да       | —                 | дифф затрагивает `.github/workflows/`, иначе `skipped` (`not_applicable`)                  |
| `test`            | `pnpm test`                               | да       | `contracts_build` | всегда                                                                                     |
| `test_int`        | `pnpm test:int`                           | да       | `contracts_build` | дифф затрагивает `apps/api/` или `packages/contracts/`; нет БД → `not_run` (`no_database`) |
| `test_scripts`    | `pnpm test:scripts`                       | да       | —                 | дифф затрагивает `scripts/`, иначе `skipped`                                               |
| `check_harness`   | `pnpm check:harness`                      | да       | —                 | дифф затрагивает `.pi/`, `scripts/cycle-*`, `AGENTS.md`; иначе `skipped`                   |
| `format_check`    | `pnpm format:check`                       | да       | —                 | всегда                                                                                     |
| `secrets_scan`    | встроенный (`scanSecrets`)                | да       | —                 | всегда                                                                                     |

`secrets_scan` проверяет только добавленные строки диффа: PEM-заголовки приватных ключей,
`AKIA[0-9A-Z]{16}`, JWT, `postgres://user:pass@` с непустым не-шаблонным паролем, присвоения
`secret|token|password|api_key` строковым литералом ≥12 символов, кроме явных заглушек
(`example`, `changeme`, `xxx`, `<…>`) и файла `.env.example`. Находка → `fail`, `file:line`
в логе без значения.

Гейты запускаются с `TURBO_FORCE=true` (`gateEnv`): `pass` в `gates.<n>.json` — это живой
прогон, а не результат из кэша turbo («FULL TURBO»). Кэш turbo адресуется по хешу входов,
но часть окружения в хеш не входит, а гейты — основное свидетельство «код проверен»;
цена принудительного прогона в этом репозитории — секунды (contracts_build 3 с,
typecheck 11 с, lint 9 с, test 12 с против миллисекунд из кэша, #216). Затрагивает только
задачи turbo: `test_int` в `turbo.json` уже `cache: false`, а `check_arch`, `check_harness`,
`format_check`, `lint:workflows` и `test:scripts` кэша не имеют.

**Окружение гейта (ADR [0007](./adr/0007-gate-env.md)).** По умолчанию гейт — доверенный код
проекта: он наследует окружение вызывающего процесса целиком плюс `TURBO_FORCE=true`, поэтому
`test_int` получает `DATABASE_URL` из окружения, как и раньше. Гейт может **объявить** окружение
полем `env` в своей записи:

```json
{
  "id": "format_check",
  "executable": "pnpm",
  "args": ["exec", "prettier", "--check", "."],
  "env": { "allow": ["npm_config_cache"], "set": { "CI": "1" } }
}
```

`allow` — имена переменных, наследуемых из окружения вызывающего; `set` — литеральные значения
(секретов там нет: конфиг лежит в git). Объявил `env` — наследование выключается: гейт получает
только `allow`, `set` и служебные `PATH`, `HOME`, `TMPDIR`; `TURBO_FORCE=true` ставится последним и
не переопределяется. Пустой `env: {}` — валидное объявление «только служебные». Схема строгая:
неизвестное подполе (`inherit`, `except`), не-массив в `allow`, пустое имя, дубль имени, не-строка в
`set`, `env` у `builtin`-гейта — код 2. Изоляции это не даёт (гейт по-прежнему может прочитать
`.env` и сходить в сеть) и «безопасным по умолчанию» не является: в CI это способ не отдавать
`NPM_TOKEN` и ключи деплоя гейтам, которым они не нужны. Секреты, которые гейту всё-таки нужны,
держат в отдельном job: объявление окружения отвечает на вопрос «что отдать», а не «как не пустить».
Сам конфиг гейтов — исполняемый код, поэтому его правку стоит видеть в ревью: если он перечислен в
`integrity.protectedPaths` (§5.2), правка попадает в `evidence/integrity.json` и в «Проверки» PR.
Allowlist по умолчанию отклонён: он ломает документированный `test_int` и десятки переменных
`turbo`/`pnpm`/`node`.

`test_int` запускает `pnpm test:int` как есть: turbo пробрасывает `DATABASE_URL`, задача зависит
от `db:generate` и не кэшируется; скрипт `.env*` не читает, поэтому `DATABASE_URL` экспортируется
в окружение процесса перед запуском цикла (`docs/environment.md`). Без переменной тесты падают
с ошибкой конфигурации и гейт получает `fail` — это не `not_run (no_database)`, то есть разные
исходы для решения. Класс отказа определяется по логу:
ошибки соединения (`ECONNREFUSED`, `ENOTFOUND`, Prisma `P1001`, «Can't reach database server»)
→ `not_run`, причина `no_database`; любые другие падения, включая
`password authentication failed`, → `fail`. Образцы логов — в фикстурах тестов.

Выход скрипта: `0` — обязательных `fail` нет; `1` — есть; `2` — внутренняя ошибка.

### 5.6 `cycle-decide.mjs`

```
node scripts/cycle-decide.mjs --dir D [--iteration N]
```

Читает `state.json`, `gates.<n>.json`, `review.<n>.md`, `evaluation.<n>.md`, `qa-web.json`
и (необязательно) `evidence/integrity.json`.
Из md извлекается последний блок ```json, валидируется и записывается нормализованным
`review.<n>.json` / `evaluation.<n>.json`. Пишет `decision.<n>.json`.

```
0. Стоимость цикла по `usage.json` выше `LIMITS.maxCycleCostRub` (§5.2, §11)
     → ESCALATE(budget). Проверяется первым: цикл дороже порога не тратит на доработки.
1. Невалидный вывод агента (нет блока, JSON не парсится, схема нарушена):
     stage = первый невалидный из [REVIEW, EVALUATE]
     retries[stage] < 1  → RETRY_STAGE(stage)
     иначе               → ESCALATE(agent_output_invalid)
   Причина дополняется путями полей для починки (#247): до 5 строк
   `invalid:<STAGE> <файл>: <путь поля>: <что не так>`, без повторов; полный список
   ошибок схемы CLI печатает в stderr, поэтому артефакт остаётся коротким.
2. Блокеры (каждый обязан быть валиден, иначе downgraded → FOLLOW-UP):
   a. required-гейт со status = fail                                       → gate:<id>
   b. review: BLOCKER, валиден если file, repro, ref разрешается, !preexisting
              MAJOR,   валиден если то же и in_scope
   c. evaluation: критерий unmet — валиден, если ≥1 ссылка в evidence разрешается
                  defect BLOCKER|MAJOR — валиден, если есть repro и ≥1 разрешаемая ссылка
   Неразрешаемые ссылки: счётчик unresolved_refs (метрика); сам элемент не блокирует.
3. Есть блокеры:
     iteration < max_iterations → REWORK
     иначе                       → ESCALATE(iteration_limit)
4. Нет блокеров. unverified = required-гейты not_run (кроме no_database) ∪ web-дифф без qa-web done
                              ∪ критерии unverified ∪ evaluation.unverified
                              ∪ факты integrity (§5.4, #36)
   (у `qa-web not_run (<reason>)`: `reason` из файла, `web-diff` — файла нет,
   `reason_missing` — причина пуста, #30)
   unverified ≠ ∅:
     есть исполнимое (required-гейт not_run не по no_database; QA не выполнен при web-диффе;
     правка защищённых файлов или удаление теста) и retries.evidence < 1
       → ACQUIRE_EVIDENCE(acquire: [...])
     иначе                    → PROCEED_WITH_UNVERIFIED
5. Иначе → PROCEED
```

**Целостность проверок (#36).** Если в пакете есть `evidence/integrity.json` (§5.4), его
факты входят в правило 4 и никогда — в правило 2: правка проверок не блокер, но и не
«проверено». Строки `unverified[]`: `integrity: protected <путь> (<added|modified|deleted>)` для
каждого затронутого защищённого файла, `integrity: tests deleted <путь>` для каждого удалённого
теста и одна сводка `integrity: tests changed (<N>)` на добавленные и изменённые тесты. Первые
две группы добавляют `acquire: integrity`; сводка по обычной правке тестов — нет. У `integrity`
в `acquire[]` нет исполнимого шага (это не гейт и не QA): добор означает повторный `REVIEW`
с явным вопросом «не ослаблены ли проверки», поэтому `cycle-state` исполняет его как повтор
этапа по Приложению B. Файла нет (правил `integrity` в проекте нет) — правило не срабатывает;
битый файл — код 2, как у `qa-web.json`.

`partial` у критерия блоком не является: попадает в `notes`. Вердикт модели
`REWORK` без валидного блокера записывается как `verdict_without_evidence` и не блокирует.
Бюджет (правило 7 спеки, правило 0 этого расчёта) — единственное правило, которое
проверяется раньше агентских: стоимость считается по накопленному `usage.json` и
`evals/prices.json` (`cost.mjs`), потому что на момент DECIDE `metrics.json` ещё не
написан (§5.8). Порог — `LIMITS.maxCycleCostRub` (30 ₽, обоснование в §11
`docs/orchestrator.md`); сравнение строгое (`> `), `costRub = null` (нет замера,
неизвестна модель или цены) означает «проверять нечего», а не ноль. В `reasons[]`
причина эскалации пишется как `escalate:budget` — её разбирает `cycle-state`;
строка с числами (`budget: 31.05 ₽ > 30 ₽`) идёт рядом для владельца.
Сопоставление находок для метрик: тот же файл и разница строк ≤ 5 → «совпали».

Результат `decision.<n>.json`:
`{ iteration, action, retry_stage|null, acquire[], reasons[], rework_items[], unverified[], downgraded[], counts{}, unresolved_refs }`.
Коды выхода: `0` решение записано; `2` ошибка.

### 5.7 `cycle-pr-body.mjs`

```
node scripts/cycle-pr-body.mjs --dir D [--draft-escalation]
```

Собирает тело PR по `.github/PULL_REQUEST_TEMPLATE.md` из фактов: «Проверки» — по
`gates.<n>.json` (не чекбоксы от руки) и, если в пакете есть `evidence/integrity.json`, строки
о правках тестов и защищённых файлов (`Тесты: изменено 2 (…); удалено 1 (…)`; при чистых
списках — «правок нет»; длинный список сворачивается в «и ещё N»), раздел «Независимая оценка» — вердикт, таблица
критериев со статусами и ссылками, `unverified` и `partial`, число итераций, расхождения
ревью и оценки; «Риски» — пункты раздела «Риски» из шаблона PR проекта (`paths.prTemplate`,
чекбоксы переносятся как есть: их отмечает человек; своего списка рисков ядро не держит);
«Вне скоупа» — из `followups.md`; строка `Closes #<issue>` обязательна.
С `--draft-escalation` в начале добавляется баннер с причинами и открытыми замечаниями.
Вывод — stdout. Для `PROCEED_WITH_UNVERIFIED` добавляется блок «не проверено» с чекбоксами
для владельца; один факт из `decision.unverified[]` (`evaluation unverified: <what>`) и
`evaluation.unverified[]` (`<what> — <why>`) печатается один раз — в более полной
формулировке (нормализация без префикса источника, #204).

`followups.md` читается только если существует к моменту сборки: замечания вне скоупа
супервизор записывает **до** `cycle-pr-body` (Приложение B, `PROCEED*`), иначе раздел
останется заглушкой при написанном позже файле.

`paths.prTemplate` пуст или в шаблоне нет раздела «Риски» — раздел печатается с пометкой
и без пунктов: чужой список рисков в PR хуже пустого (риски — свойство проекта, а не ядра).

### 5.8 `cycle-metrics.mjs` (минимум фазы 1)

Пишет `metrics.json`: длительности этапов (из `state.history`), длительности гейтов,
число итераций, исходы гейтов, замечания по серьёзности, дефекты оценщика, `only_review` /
`only_evaluator` / `both`, `unresolved_refs`, `verdict_without_evidence`,
`evaluator_shares_family_with_plan: true`. `tokens` и `cost_rub` берутся из `usage.json`
каталога цикла: `tokens` — суммы по этапам (пишет `cycle-usage` по транскриптам субагентов),

`cost_rub: null`, потому что неполная сумма выдавала бы себя за полную. Блок `driver` (#47) —
счётчики журнала `driver.jsonl`: `steps` (решений выдано), `executed` (исполнено драйвером),
`handed_off` (`spawn`/`handoff` супервизору), `mismatch` (расхождений с ответом драйвера).
Журнала нет — блока нет: цикл вели без драйвера, и выдумывать нули нельзя.

### 5.9 `check-harness.mjs`

Читает файлы профиля раскладки (ADR 0005): `paths.agentsDir/*.md` (frontmatter между `---`,
строки `key: value`, значения в кавычках допустимы, `tools` — список через запятую),
`paths.settings`, `paths.cyclePrompt`, `paths.agentsMd`. По умолчанию это `.pi/agents/*.md`,
`.pi/settings.json`, `.pi/prompts/cycle.md`, `AGENTS.md`; на профиле с другими путями читается и
**называется** в выводе то, что задано в конфиге — диагностика, указывающая не на тот файл, хуже
отсутствия диагностики. Семейство = второй сегмент `model` (`polza-ai/<семейство>/<модель>`).

| Правило | Проверка                                                                                                                                        |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| H1      | агенты `plan`, `code`, `review`, `evaluate` есть; поля `name`, `model`, `thinking`, `tools` заданы; `name` = имени файла                        |
| H2      | семейство `code` ≠ `review`; семейство `evaluate` ∉ {`code`, `review`} (ребро `evaluate`↔`plan` — только предупреждение `W2`, см. ниже) |
| H3      | у `plan` нет `bash`, `edit`, `write`; у `review` и `evaluate` нет `edit`, `write`                                                               |
| H4      | все `model` начинаются с `polza-ai/`                                                                                                            |
| H5      | `subagents.maxSubagentSpawnsPerRun` ≥ 7                                                                                                         |
| H6      | `cycle.md` содержит все имена этапов автомата; `AGENTS.md` не содержит идентификаторов моделей: `deepseek`, `glm-?\d`, `gpt-?\d`, `claude-(opus | sonnet | haiku | fable)`, `polza-ai/` (без учёта регистра; название продукта «Claude Code» нарушением не считается) |

Выход: `0` всё соответствует (возможны предупреждения `W2` в stderr); `1` есть нарушения (список `правило: файл — что не так`);
`2` ошибка чтения. До T7 `H6` по `AGENTS.md` ожидаемо красный, поэтому в CI скрипт
подключается в T7.

Корень проверки — текущий каталог (`--root <dir>` его подменяет, #42): у потребителя bin
`harness-check-layout` лежит в `node_modules`, и проверять оттуда каталог пакета вместо проекта
было бы ошибкой; в репозитории ядра cwd и есть его корень, поэтому самопроверка в CI и в
pre-commit не меняется. Фикстурные деревья тестов адресуются `--root`.

Ребро `evaluate`↔`plan` H2 намеренно не проверяет: совпадение семейств — принятый риск I3
(`docs/orchestrator.md` §4, §18). Но невидимый риск дрейфует молча, поэтому совпадение
печатается предупреждением `W2: .pi/agents/evaluate.md — …` в stderr, код выхода остаётся `0`.
Нарушением пара станет только после смены модели оценщика (отдельное правило H7).

## Приложение A. Схемы (для валидаторов)

Общее: все ссылки — строки вида `path:line`, `gate:<id>`, `qa:<id>`; `severity` ∈
{`BLOCKER`, `MAJOR`, `MINOR`, `FOLLOW-UP`}; лишние поля игнорируются, отсутствующие
обязательные — ошибка.

**state.json**

| Поле                          | Тип и правила                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| `issue`                       | целое > 0                                                                                                |
| `slug`                        | строка `^[a-z0-9-]{1,60}$`                                                                               |
| `branch`                      | строка                                                                                                   |
| `base_sha`                    | 40 hex                                                                                                   |
| `iteration`, `max_iterations` | целые ≥ 1, `iteration ≤ max_iterations` (кроме `owner_approved`)                                         |
| `stage`                       | INIT, PLAN, CODE, GATES, QA_WEB, REVIEW, EVALUATE, DECIDE, REWORK, ACQUIRE_EVIDENCE, PR, DONE, ESCALATED |
| `stage_status`                | pending, running, done, error                                                                            |
| `criteria_source`             | issue, plan_owner_approved                                                                               |
| `criteria_sha256`             | `null` или 64 hex — дайджест замороженных критериев; отсутствие поля равнозначно `null`                 |
| `retries`                     | `{ REVIEW, EVALUATE, evidence }`, целые ≥ 0                                                              |
| `owner_approved`              | boolean                                                                                                  |
| `models`                      | объект строк                                                                                             |
| `history[]`                   | `{ stage, iteration, started_at, finished_at\|null, status, detail? }` — `detail` необязателен, см. ниже |
| `escalation`                  | `null` или `{ reason, detail, draft_pr_allowed }`                                                        |
| `applied_decision`            | `null` или `{ iteration, action, retry_stage\|null, digest }` — маркер применённого решения              |
| `started_at`, `updated_at`    | ISO-8601                                                                                                 |

`applied_decision` — защита `apply-decision` от повторного применения того же решения: `digest` —
`sha256` канонического JSON `decision.<n>.json` (ключи отсортированы, поэтому дайджест не
зависит от порядка полей и артефакт остаётся побайтно воспроизводимым); совпадение всех
четырёх полей — no-op. Валидатор `state` лишние поля игнорирует, поэтому старые `state.json`
без этого поля остаются валидными.

`criteria_sha256` — заморозка критериев приёмки (#22): `sha256` пар `[id, формулировка]`
критериев из `issue.json`, пишется `cycle-state freeze-criteria`. Сверка идёт в четырёх местах:
`cycle-evidence criteria` (критерии из issue против закреплённых — расхождение код 2, файлы не
перезаписываются), `cycle-evidence packet` (пакет — вход судьи), `cycle-decide` (до применения
правил) и `cycle-pr-body` (публикуемая цель) — расхождение везде код 2 `criteria_drift`.
Поле необязательное: `null` и отсутствие равнозначны «не заморожено», старые `state.json`
остаются валидными, мусор в поле — ошибка схемы.

`history[].detail` — необязательное поле закрытой записи, пишется `cycle-state` в двух случаях:
`finish --detail T` (человеческий текст, маскируется по §5.4, как свободный текст лога) и
`escalate` (туда попадает причина эскалации из словаря D7). У открытой записи
(`finished_at: null`) поля нет; валидатор `state` лишние поля игнорирует, поэтому старые
артефакты без `detail` остаются валидными. Метрики на поле не опираются.

**gates.\<n\>.json**: `iteration`, `base_sha`, `head`, `started_at`, `gates[]`:
`{ id, cmd|null, required, status ∈ {pass, fail, skipped, not_run}, exit|null, duration_s, log|null, reason|null }`.
`reason`: `not_applicable`, `no_database`, `timeout`, `tool_missing`, `blocked_by:<id>`.

**review** (блок в `review.<n>.md`): `verdict ∈ {merge-ready, needs-changes}`,
`findings[]`: `{ id, severity, file, line, summary, repro, in_scope, preexisting }`
(`file`, `line`, `repro` могут быть пустыми только у MINOR и FOLLOW-UP).

**evaluation** (блок в `evaluation.<n>.md`): `verdict ∈ {ACCEPT, ACCEPT_WITH_FOLLOWUPS, REWORK, INSUFFICIENT_EVIDENCE}`;
`criteria[]`: `{ id, status ∈ {met, partial, unmet, unverified}, evidence[], note }`, id из `criteria.md`;
`scores`: `coverage, correctness, tests, data, pii_security, architecture, scope, docs, evidence` — 0–3 или `null`;
`defects[]`: `{ id, severity ∈ {BLOCKER, MAJOR, MINOR}, claim, evidence[], repro }`;
`unverified[]`: `{ what, why, how_to_verify }`.

**qa-web.json**: `status ∈ {done, not_run}`, `reason`, `steps[]`: `{ id, url, action, observed, console_errors[], failed_requests[], cache_headers }`.
Связка полей проверяется схемой (#30): `done` требует хотя бы один шаг, `not_run` — непустой
`reason` и пустой `steps`; шаг `not_run` ссылкой `qa:<id>` не разрешается.

**evidence/integrity.json** (#27): `{ test_paths[], protected_paths[], tests, protected }`, где
`tests` и `protected` — `{ added[], modified[], deleted[] }` с непустыми строками-путями;
порядок путей — сортировка по строке, порядок ключей артефакта фиксирован. Пишет только
`cycle-evidence packet` и только при заданных правилах `integrity`.

**decision.\<n\>.json**: см. §5.6; `action ∈ {REWORK, ACQUIRE_EVIDENCE, RETRY_STAGE, PROCEED, PROCEED_WITH_UNVERIFIED, ESCALATE}`.

**escalation.json**: `{ reason ∈ D7, detail, draft_pr_allowed, open_items[] }`.

**metrics.json** (добавлено в T8): счётчики и длительности завершённого цикла. Значения
длительностей — секунды с точностью до 3 знаков; `cycle_duration_s` равен сумме
`stage_durations_s`, `gate_total_s` — сумме `gate_durations_s`.

| Поле                                          | Тип и правила                                                                                                                            |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `iterations`, `max_iterations`                | целые ≥ 1 (из `state.json`)                                                                                                              |
| `final_stage`                                 | `state.stage`: INIT, PLAN, …, DONE, ESCALATED                                                                                            |
| `stage_durations_s`                           | объект `<STAGE>` → число ≥ 0: сумма `finished_at - started_at` по `state.history`                                                        |
| `cycle_duration_s`                            | число ≥ 0: сумма `stage_durations_s`                                                                                                     |
| `gate_durations_s`                            | объект `<id гейта>` → число ≥ 0: сумма `duration_s` по всем итерациям                                                                    |
| `gate_total_s`                                | число ≥ 0: сумма `gate_durations_s`                                                                                                      |
| `gate_outcomes`                               | объект `<id гейта>` → `{ pass, fail, skipped, not_run }`, целые ≥ 0 (по всем итерациям)                                                  |
| `review_findings`                             | `{ BLOCKER, MAJOR, MINOR, FOLLOW-UP }`, целые ≥ 0                                                                                        |
| `evaluator_defects`                           | `{ BLOCKER, MAJOR, MINOR }`, целые ≥ 0                                                                                                   |
| `only_review`, `only_evaluator`, `both`       | целые ≥ 0: сопоставление находок и дефектов внутри итерации по правилу §5.6 (разница строк ≤ 5, каждый элемент один раз)                 |
| `unresolved_refs`, `verdict_without_evidence` | целые ≥ 0: суммы из `decision.<n>.json`                                                                                                  |
| `unclosed_stages`                             | целое ≥ 0: записи `state.history` без `finished_at`                                                                                      |
| `evaluator_shares_family_with_plan`           | boolean: семейство — второй сегмент `model` (§5.9); нет ключа `evaluate` — `true` (R2)                                                   |
| `tokens`                                      | `null` или карта «этап → `{runs, input, cache_read, cache_write, output, reasoning}`»; этапы только `plan`, `code`, `review`, `evaluate` |
| `cost_rub`                                    | `null` или число ≥ 0 (₽, копейки): те же токены по `evals/prices.json` и `state.models`                                                  |
| `driver`                                      | необязательный блок: `{ steps, executed, handed_off, mismatch }`, целые ≥ 0 — сводка журнала `driver.jsonl` (§5.3a); нет журнала — нет блока |

## Приложение B. Протокол супервизора (канонический порядок команд)

Супервизор вызывает команды и выполняет `action` из `decision`, ничего не решая сам.
Маршрутизацию стадий с #47 отдаёт `cycle-driver next`: он отвечает, какая стадия следующая и
что именно делать, а супервизор исполняет. Команды ниже приведены в том же порядке — драйвер
выдаёт их же, поэтому расхождение таблицы и кода видно по `next`.

```
INIT       gh issue view N --json title,body,labels > <dir>/issue.json
           node scripts/cycle-state.mjs lock
           node scripts/cycle-state.mjs init --issue N --slug S --branch B
           node scripts/cycle-evidence.mjs criteria --dir <dir> --issue-json <dir>/issue.json
             (код ≠ 0 → cycle-state escalate --reason criteria_missing; комментарий в issue; стоп)
           node scripts/cycle-state.mjs freeze-criteria
             (код 3 criteria_drift → escalate --reason criteria_drift, стоп: цель цикла
              меняет владелец; подтверждение — freeze-criteria --owner-approved)
PLAN       advance --to PLAN → субагент plan → plan.<n>.md → finish
             (план просит выбрать вариант → escalate --reason plan_ambiguous)
CODE       advance --to CODE → субагент code → code-report.<n>.md → finish
GATES      advance --to GATES → node scripts/cycle-gates.mjs --dir <dir>
QA_WEB     только если дифф затрагивает qaWeb.pathPrefixes: advance --to QA_WEB → сценарий docs/qa-web.md
             → сырые данные в qa-web.json (с id шагов) → finish
ANALYSIS   node scripts/cycle-evidence.mjs packet --dir <dir>   (код 4 → escalate --reason diff_too_large)
           advance --to REVIEW   → субагент review   (ему plan и дифф) → review.<n>.md
           advance --to EVALUATE → субагент evaluate (только evidence/)  → evaluation.<n>.md
DECIDE     advance --to DECIDE → node scripts/cycle-decide.mjs --dir <dir> → cycle-state apply-decision
           действия по `action`:
             RETRY_STAGE            повторить указанный этап один раз
             ACQUIRE_EVIDENCE       выполнить acquire[] (гейт → GATES, qa-web → QA_WEB,
                                    integrity → повтор REVIEW), затем снова ANALYSIS
             REWORK                 rework-brief.<n>.md из rework_items → CODE (iteration+1)
             PROCEED[_WITH_UNVERIFIED]  followups.md (замечания вне скоупа — до сборки тела,
                                         иначе «Вне скоупа» останется пустым), коммиты, push,
                                         PR: тело из cycle-pr-body, метка status:review
             ESCALATE               комментарий в issue, status:blocked + needs-owner;
                                    cycle-state unlock; draft PR только если escalation.draft_pr_allowed
DONE       node scripts/cycle-metrics.mjs --dir <dir>; cycle-state unlock
```

Супервизору нельзя: менять `state.json` руками, пересматривать `action`, пропускать этапы,
показывать оценщику `plan.*`, `review.*`, `code-report.*`, мержить PR.
