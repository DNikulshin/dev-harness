# Релизы и версии пакета

Норматив для `@dnikulshin/harness`: что считается публичным API, как объявляется несовместимое
изменение и как выпускается версия. Процесс работы — [workflow.md](./workflow.md), устройство ядра —
[protocol.md](./protocol.md).

## Публичный API

Публично ровно то, что объявлено в `package.json`: ключи `exports`, `bin` и **схемы данных**, на
которые эти команды опираются. Всё остальное — внутреннее, даже если физически лежит в архиве.

| Что                                 | Где объявлено                                                                                    | Обещание                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `bin` (16 команд)                   | `package.json#bin`                                                                               | имя команды и её флаги стабильны; коды выхода — контракт для CI потребителя          |
| Точки входа `exports`               | `package.json#exports`                                                                           | импорт модуля и его именованные экспорты; `types` из `types/`                        |
| `scripts/lib/cycle/config`          | `exports` (единственный шов библиотеки)                                                          | `loadConfig`, `takeConfigOption`, пути конфига, `ConfigError`                        |
| Схемы артефактов                    | [orchestrator-core.md, Приложение A](./orchestrator-core.md#приложение-a-схемы)                  | имена файлов (`state.json`, `gates.<n>.json`, `decision.<n>.json`, …) и поля         |
| Поля конфига                        | [orchestrator-core.md §5.2](./orchestrator-core.md), `templates/.pi/harness.config.example.json` | секции и поля `.pi/harness.config.json`, строгая валидация (неизвестное — код 2)     |
| Имена флагов CLI и переменных среды | `--help` команд, этот раздел                                                                     | `--config`/`HARNESS_CONFIG`, `HARNESS_LIMIT_*`, `--max-cost-rub`, `--max-iterations` |
| Раскладка артефактов установки      | `harness.version`, `harness-init`                                                                | формат файла версии и правило «дайджест совпал — файл наш»                           |

Закрыто и меняется свободно: `scripts/lib/**` (кроме шва), тесты и фикстуры, `scripts/**` вне
`exports`, `tooling/**`, `.github/**`, внутренние документы `docs/local/**`. Импорт закрытого пути
даёт `ERR_PACKAGE_PATH_NOT_EXPORTED` — это проверяется тестом (`scripts/package-exports.test.mjs`) и
тестом на установленном пакете.

## Что считается несовместимым изменением

Несовместимо (major) всё, что ломает уже написанного потребителя:

- удалить или переименовать `bin`, флаг, ключ `exports`, именованный экспорт;
- изменить смысл существующего поля конфига или сделать ранее валидный конфиг невалидным (новое
  обязательное поле, ужесточение типа, новое запрещённое значение);
- изменить имена или обязательность полей артефактов, которые читает UI/адаптер;
- изменить код выхода команды на том же входе (CI потребителя завязан на коды).

Совместимо (minor) — новое поле с умолчанием, новый необязательный флаг, новый ключ `exports`, новая
команда, новое предупреждение. Совместимо (patch) — исправление, при котором входы и выходы описаны
теми же правилами.

Правило проверки: изменение совместимо, если конфиг, артефакты и вызовы команд прошлой версии
работают без правок. Сомнение трактуется как несовместимость: сломанный потребитель дороже лишнего
major.

## Процесс выпуска

1. **Релизный issue** с пометкой `type:chore`: что вошло, какая версия, что ломается.
2. **PR** поднимает `version` в `package.json` и, если менялся публичный API, — этот документ и
   README. Merge — только владелец.
3. **Тег** `vX.Y.Z` на `main` после зелёного `checks`: `git tag -a vX.Y.Z -m "vX.Y.Z"` и
   `git push origin vX.Y.Z`. Версия в `package.json` и в теге совпадают.
4. **Публикация** — автоматически, workflow `release.yml`: `pnpm check` → `pnpm pack` →
   `tooling/check-package.mjs` (состав архива, обещания `bin`/`exports`, версия против тега) →
   `npm publish --provenance --access public` с секретом `NPM_TOKEN`.
5. **Проверка после публикации** — в чистом каталоге: `npx @dnikulshin/harness init` (создаёт
   шаблоны, конфиг и проверяет раскладку) и `npm view @dnikulshin/harness version`.
6. **Release notes** на GitHub: что вошло, как обновиться, что ломается — несовместимое изменение
   называется явно, иначе потребитель узнаёт о нём из падения CI.

Ошибочный тег не перезаписывается (ruleset `release-tags`): публикуется следующая версия, а в
release notes сказано, чем она отличается. Версия в npm неизменяема — это и есть причина, по которой
состав архива проверяется до публикации.

## Что проверяется механизмом

| Проверка                                    | Где                                                              |
| ------------------------------------------- | ---------------------------------------------------------------- |
| Каждый `bin` имеет ключ `exports` с типами  | `scripts/package-exports.test.mjs`                               |
| Архив полон, инфраструктура не уехала       | `scripts/package-consumer.test.mjs`, `tooling/check-package.mjs` |
| Установка из архива, `bin`, `exports`, типы | `scripts/package-consumer.test.mjs`                              |
| Версия в архиве совпадает с тегом           | `tooling/check-package.mjs --tag` в `release.yml`                |
| Конфиг вне умолчания находится по флагу     | `scripts/lib/cycle/config.test.mjs`, `harness-init.test.mjs`     |
