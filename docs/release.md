# Релизы и версии пакета

Норматив для `@dnikulshin/harness`: что считается публичным API, как объявляется несовместимое
изменение и как выпускается версия. Процесс работы — [workflow.md](./workflow.md), устройство ядра —
[protocol.md](./protocol.md).

## Публичный API

Публично ровно то, что объявлено в `package.json`: ключи `exports`, `bin` и **схемы данных**, на
которые эти команды опираются. Всё остальное — внутреннее, даже если физически лежит в архиве.

| Что                                 | Где объявлено                                                                                    | Обещание                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `bin` (16 команд)                   | `package.json#bin`                                                                               | имя команды и её флаги стабильны; коды выхода — контракт для CI потребителя          |
| Точки входа `exports`               | `package.json#exports`                                                                           | импорт модуля и его именованные экспорты; `types` из `types/`                        |
| `scripts/lib/cycle/config`          | `exports` (единственный шов библиотеки)                                                          | `loadConfig`, `takeConfigOption`, пути конфига, `ConfigError`                        |
| Схемы артефактов                    | [orchestrator-core.md, Приложение A](./orchestrator-core.md#приложение-a-схемы)                  | имена файлов (`state.json`, `gates.<n>.json`, `decision.<n>.json`, …) и поля         |
| Поля конфига                        | [orchestrator-core.md §5.2](./orchestrator-core.md), `templates/.pi/harness.config.example.json` | секции и поля `.pi/harness.config.json`, строгая валидация (неизвестное — код 2)     |
| Имена флагов CLI и переменных среды | `--help` команд, этот раздел                                                                     | `--config`/`HARNESS_CONFIG`, `HARNESS_LIMIT_*`, `--max-cost-rub`, `--max-iterations` |
| Раскладка артефактов установки      | `harness.version`, `harness-init`                                                                | формат файла версии и правило «дайджест совпал — файл наш»                           |

Закрыто и меняется свободно: `scripts/lib/**` (кроме шва), тесты и фикстуры, `scripts/**` вне
`exports`, `tooling/**`, `.github/**`, внутренние документы `docs/local/**`. Импорт закрытого пути
даёт `ERR_PACKAGE_PATH_NOT_EXPORTED` — это проверяется тестом (`scripts/package-exports.test.mjs`) и
тестом на установленном пакете.

## Что считается несовместимым изменением

Несовместимо (major) всё, что ломает уже написанного потребителя:

- удалить или переименовать `bin`, флаг, ключ `exports`, именованный экспорт;
- изменить смысл существующего поля конфига или сделать ранее валидный конфиг невалидным (новое
  обязательное поле, ужесточение типа, новое запрещённое значение);
- изменить имена или обязательность полей артефактов, которые читает UI/адаптер (кто именно читает
  схему — раздел «Читатели схемы артефактов» ниже);
- изменить код выхода команды на том же входе (CI потребителя завязан на коды);
- изменить значение `action` в `decision.<n>.json` на тех же входах: ядро детерминированное, поэтому
  такое изменение меняет поведенческий контракт пакета, даже если схема JSON прежняя (пример —
  `PROCEED` → `PROCEED_WITH_UNVERIFIED` в 0.2.0);
- сузить заявленные платформы или версию Node (`os`, `engines` в `package.json`): установка на ранее
  работавшей системе начинает отказывать.

**`engines` — это то, что гоняет CI.** Цифра в `engines` подтверждена прогоном, а не намерением:
нижняя граница проверена матрицей CI, верхняя не ставится — версия, которую CI не гоняет, ничего не
обещает, и запрещать на ней установку не за что. Отсюда правила: расширять поддержку вниз (22, 24) —
только вместе с матрицей CI по версиям Node и в том же изменении; сужать (поднимать нижнюю границу)
— несовместимое изменение по правилу выше (#203).

Совместимо (minor) — новое поле с умолчанием, новый необязательный флаг, новый ключ `exports`, новая
команда, новое предупреждение, расширение заявленных платформ (новый элемент `os`, под который есть
CI-прогон). Совместимо (patch) — исправление, при котором входы и выходы описаны теми же правилами.

Правило проверки: изменение совместимо, если конфиг, артефакты и вызовы команд прошлой версии
работают без правок. Сомнение трактуется как несовместимость: сломанный потребитель дороже лишнего
major.

**Строки `unverified[]` и `reasons[]` — непрозрачный текст.** Префиксы (`gate:`, `qa-web`,
`criteria:`, `unproven:`, `evaluation unverified:`, `integrity:`) — внутренний формат ядра:
потребитель вправе печатать строку и считать её количество, но не разбирать содержимое. Разбор есть
только внутри ядра (`scripts/lib/cycle/unverified.mjs` — снятие префикса для дедупликации). Новый
префикс сам по себе несовместимым изменением не является (0.2.0, #125/#133).

## Читатели схемы артефактов

Схему артефактов ([Приложение A](./orchestrator-core.md#приложение-a-схемы)) читают снаружи ядра
двое, и ни один из них ядро не импортирует:

| Читатель               | Где живёт                                                                                                                                       | Что делает с файлами                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Адаптер рантайма       | `@dnikulshin/pi-harness` (ADR [0008](./adr/0008-adapter-repository.md))                                                                         | вызывает `bin` ядра, читает `state.json` и решения |
| Просмотрщик артефактов | [`dnikulshin/dnikulshin-harness-viewer`](https://github.com/DNikulshin/dnikulshin-harness-viewer) (ADR [0013](./adr/0013-viewer-repository.md)) | читает `state.json`, гейты, решения, `evidence/`   |

Поэтому правка имён или обязательности полей артефактов видна не в CI этого репозитория, а у
потребителя: читатель разберёт знакомое поле, а нового не увидит и покажет неполный блок.

Порядок — **сначала ядро, потом читатели**: релиз ядра с изменением схемы (major и явная запись в
release notes), затем отдельный PR читателя. Обратный порядок ломает читатель на текущей версии
ядра. Правила чтения в читателях не копируются: и адаптер, и просмотрщик ссылаются на этот документ
и на Приложение A.

## Процесс выпуска

1. **Релизный issue** с пометкой `type:chore`: что вошло, какая версия, что ломается.
2. **PR** поднимает `version` в `package.json` и, если менялся публичный API, — этот документ и
   README. Merge — только владелец.
3. **Тег** `vX.Y.Z` на `main` после зелёного `checks`: `git tag -a vX.Y.Z -m "vX.Y.Z"` и
   `git push origin vX.Y.Z`. Версия в `package.json` и в теге совпадают.
4. **Публикация** — автоматически, workflow `release.yml`: `pnpm check` → `pnpm pack` →
   `tooling/check-package.mjs` (состав архива, обещания `bin`/`exports`, версия против тега) →
   `npm publish --provenance --access public` по **trusted publishing (OIDC)**.

   Долгоживущего секрета с правом публикации нет (решение — issue #212): `release.yml` берёт
   короткоживущий токен из OIDC-обмена (`id-token: write`), а npm проверяет, что публикует именно
   этот репозиторий и именно этот файл workflow. Связку ставит владелец один раз:

   ```bash
   npm trust github @dnikulshin/harness --file release.yml --allow-publish
   npm trust list @dnikulshin/harness   # что настроено
   ```

   То же самое есть в npmjs.com: пакет → Settings → Trusted publishing.

   Что важно знать про связку:

   - **первая успешная публикация — в течение 2 суток** после создания, иначе конфиг истекает и его
     надо создавать заново. Поэтому связка заводится под релиз, а не про запас;
   - существующую связку **нельзя редактировать** — смена прав это удалить и создать заново (и снова
     2 суток);
   - **имя файла `release.yml` — часть доверия.** Переименовали файл — пересоздали связку; npm видит
     расхождение только в момент публикации, отказ выглядит как `ENEEDAUTH`;
   - провенанс при OIDC генерируется автоматически (`publishConfig.provenance` тоже включён);
   - `npm view` работает анонимно, а `npm stage list/view/approve/reject` OIDC-токеном — нет:
     подтверждение staged-версии — только интерактивно (CLI владельца или npmjs.com).

   Старый npm ловится первым шагом workflow — до тестов и сборки: trusted publishing требует npm ≥
   11.5.1, на более старом CLI `npm publish` падает `ENEEDAUTH`, и по тексту не видно, что виновата
   версия.

   На уровне пакета включено «Require two-factor authentication and disallow bypass 2FA tokens»
   (npmjs.com → пакет → Settings → Publishing access). Следствие важнее, чем звучит: токеном из CI
   публиковать нельзя — bypass-2FA токены запрещены настройкой пакета, а токен без bypass требует
   OTP, которого в CI нет. Аварийный путь поэтому не «секрет плюс шаг в workflow», а ручная
   публикация владельцем: локально `pnpm pack` →
   `node tooling/check-package.mjs dist/*.tgz --tag vX.Y.Z` →
   `npm publish ./dist/<архив>.tgz --otp <код>` (либо `npm stage publish` + `npm stage approve`).
   Возвращать `NPM_TOKEN` в секреты для этого не нужно и не следует.

5. **Проверка после публикации** — в `release.yml`: версия из тега проверяется в реестре
   (`npm view @dnikulshin/harness@X.Y.Z version`, 10 попыток по 30 с) и отсутствие версии валит
   прогон, а не считается выпуском. Почему вывод `npm publish` доказательством не является — раздел
   «stage и publish». Отдельно, в чистом каталоге: `npx @dnikulshin/harness init` (создаёт шаблоны,
   конфиг и проверяет раскладку) и `npm view @dnikulshin/harness version`.
6. **Release notes** на GitHub: что вошло, как обновиться, что ломается — несовместимое изменение
   называется явно, иначе потребитель узнаёт о нём из падения CI.

Ошибочный тег не перезаписывается (ruleset `release-tags`): публикуется следующая версия, а в
release notes сказано, чем она отличается. Версия в npm неизменяема — это и есть причина, по которой
состав архива проверяется до публикации.

## stage и publish

Публикация может пройти в два шага: `npm publish` (или `npm stage publish`) кладёт версию в staging,
а в общий реестр она попадает только после подтверждения человеком с 2FA — так устроено staged
publishing ([npm stage](https://docs.npmjs.com/cli/v11/commands/npm-stage/)). Потребитель до
подтверждения продолжает видеть прежнюю версию: `npm view @dnikulshin/harness version` отдаёт
старую, а запрос точного номера — `E404`.

**Зелёный прогон не доказывает публикацию.** `npm publish` завершается кодом 0 и печатает
`+ @dnikulshin/harness@X.Y.Z` и тогда, когда версия легла в staging. Ровно так выпускалась 0.2.1:
job — `success`, в логе `+ @dnikulshin/harness@0.2.1`, а через 15 минут в реестре по-прежнему только
0.2.0 (issue #205). Версия появилась только 22.11 04:46 — то ли после подтверждения, то ли после
задержки реестра; на что именно списать те 15 минут, задним числом не установить. Поэтому
`release.yml` после `npm publish` проверяет факт: `npm view @dnikulshin/harness@<версия> version` с
ретраями (10 × 30 с). Версии нет — job падает с текстом «Опубликовано не было» и ссылкой на
staged-список, а не считает релиз выпущенным.

Что видно снаружи:

| Проверка                   | До подтверждения  | После      |
| -------------------------- | ----------------- | ---------- |
| `npm view … version`       | предыдущая версия | выпущенная |
| `npm view …@X.Y.Z version` | `E404`            | версия     |
| `npm stage list`           | staged-запись     | пусто      |

Если публикация ушла в stage:

1. `npm stage list` — какие версии ждут подтверждения (2FA не нужна — читается любым токеном);
2. `npm stage view <stage-id>` — что именно в архиве;
3. `npm stage approve <stage-id>` — опубликовать (спросит OTP) или `npm stage reject <stage-id>` —
   снять версию совсем;
4. **Не перезапускать `release.yml` до решения.** Staged-запись занимает тот же номер в
   semver-индексе пакета: повторная публикация того же `X.Y.Z` откажет, а не перезапишет. После
   `approve` перезапуск не нужен — доказательство даёт `npm view` (п.5 «Процесса выпуска»).

Способ публикации выбран — trusted publishing (OIDC), без долгоживущего токена (issue #212):
подтверждение руками в норме не нужно, а доказательство публикации даёт проверка реестра (п.5
«Процесса выпуска»). Связка разрешает и `npm stage publish` — это ручной путь для случая, когда
версию надо выпустить под своим контролем; workflow им не пользуется и публикует напрямую. Если
версия ушла в staging вручную, проверка реестра в `release.yml` покраснеет до подтверждения — это
ожидаемо, а не поломка.

Токеном из CI публиковать нельзя: на пакете включено «Require two-factor authentication and disallow
bypass 2FA tokens». Аварийный путь — та же ручная публикация владельцем с OTP, а не секрет в
репозитории (подробнее — п.4 «Процесса выпуска»).

## Отзыв ошибочного релиза

Версия в npm неизменяема: `pkg@version`, однажды использованная, не переиспользуется никогда — даже
если её отозвали. Поэтому исправление ошибки в коде — это **новый** patch и новый тег (ruleset
`release-tags` запрещает перезапись тегов, [workflow.md](./workflow.md)), а не повторная публикация
того же номера. Отзыв отвечает на другой вопрос: что делать с версией, которую потребитель уже
видит.

| Инструмент                                        | Когда                             | Что видит потребитель                                                            | Обратимость                                 |
| ------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------- |
| `npm deprecate @dnikulshin/harness@X.Y.Z "текст"` | по умолчанию                      | предупреждение при установке и на странице пакета; установка продолжает работать | да: `npm deprecate …@X.Y.Z ""` — без текста |
| `npm unpublish @dnikulshin/harness@X.Y.Z`         | исключение: версия не должна жить | версия исчезает из реестра, установка по точному номеру перестаёт работать       | нет                                         |

**`deprecate` — выбор по умолчанию.** Сборки потребителя не ломаются (в отличие от `unpublish`), а
текст сообщения — то место, где сказано, на что обновиться: «Отозвана: гейт пропускал пустой конфиг,
используйте `X.Y.Z+1`».

**`unpublish` ограничен политикой npm** (docs.npmjs.com/policies/unpublish): своя версия и одно из
двух — меньше 72 часов с публикации, либо на момент отзыва нет зависимых пакетов, меньше 300
скачиваний за неделю и единственный мантейнер. Отменить unpublish нельзя, а если снять все версии
пакета, новые публикации блокируются на 24 часа. За пределами критериев остаётся только `deprecate`
или обращение в поддержку npm.

**Операцию делает владелец локально.** Запись в реестр требует авторизации, и npm на такой операции
просит интерактивный веб-логин с 2FA. OIDC-токен `release.yml` живёт только внутри прогона и для
отзыва не переиспользуется: с ним работают лишь `npm publish`, `npm stage publish` и `npm dist-tag`.

**Тег не трогается.** `vX.Y.Z` остаётся на месте (ruleset `release-tags`), а в release notes версии
сказано, что она отозвана, чем именно и куда обновиться. Ссылка на тег в git-зависимости
(`github:…#vX.Y.Z`) продолжает резолвиться — и это ещё одна причина предпочитать `deprecate`.

**Перезапуск прогона — не отзыв.** Перезапуск `release.yml` упавшей публикации публикует **тот же**
архив из того же коммита: он годится, когда не хватало секрета или инфраструктуры (так выпускалась
0.2.0, issue #161), и бесполезен, если ошибка в коде — код в теге уже зафиксирован.

**След в реестре остаётся.** После `unpublish` версия исчезает из `versions`, но остаётся записью в
`time`-мапе манифеста: это журнал событий, а не список доступных версий, и чистить его не нужно.

Проверка после отзыва:

```bash
npm view @dnikulshin/harness@X.Y.Z deprecated   # текст сообщения (или пусто)
npm view @dnikulshin/harness dist-tags           # latest указывает на живую версию
npm view @dnikulshin/harness versions            # отозванной версии нет (только для unpublish)
```

| Проверка                                    | Где                                                              |
