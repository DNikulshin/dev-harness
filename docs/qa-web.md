# `qa-web.json` — сырые данные браузерной проверки

Документ описывает **формат** фактов, которые собирает этап `QA_WEB`, и правила, по которым с ними
работают `cycle-decide`, `cycle-evidence` и `validate.mjs`. Это не инструкция «как тестировать
браузером» — сценарий проверки задаёт проект в своём `AGENTS.md`.

Нормативные соседи: `docs/orchestrator.md` §5 (артефакты), §6 (автомат), §9 (решения);
`docs/orchestrator-core.md` §5.6 (правила решения) и Приложение A (схемы).

## Зачем отдельный артефакт

Субагент, который правил код, не может быть источником свидетельства о том, что «в браузере всё
работает»: его отчёт — это суждение, а не факт. Поэтому браузерная проверка вынесена в отдельный
этап, а её результат — в файл с сырыми наблюдениями: URL, действие, что увидели, ошибки консоли,
упавшие запросы. Решение по этим данным принимает код, а не текст.

## Когда этап запускается

Этап `QA_WEB` существует в автомате (`GATES → QA_WEB → REVIEW`), но нужен не всегда:

- проект задаёт в `.pi/harness.config.json` префиксы путей, при которых дифф считается затрагивающим
  web:

  ```json
  { "qaWeb": { "pathPrefixes": ["apps/frontend/", "packages/ui"] } }
  ```

- `cycle-decide` строит список изменённых файлов от `state.base_sha` и сравнивает с префиксами
  (`diffTouchesWeb`): совпадение по файлу или по каталогу (`apps/frontend/x.ts` ⊂ `apps/frontend/`,
  `packages/ui` = `packages/ui` без завершающего слэша);
- пустой список префиксов (значение по умолчанию) — этап не нужен никогда: дифф web не затрагивает;
- затрагивает, а `qa-web.json` нет или `status ≠ done` — `cycle-decide` добавляет
  `qa-web not_run (<причина>)` в `unverified[]` и `qa-web` в `acquire[]` (правило 4 §5.6): сначала
  добор свидетельств (`ACQUIRE_EVIDENCE`), и только потом `PROCEED_WITH_UNVERIFIED`.

## Схема

Файл лежит в каталоге цикла: `<dir>/qa-web.json` (`FIXED_NAMES.qaWeb`). Валидатор — `validateQaWeb`
в `scripts/lib/cycle/validate.mjs`; расхождение со схемой — ошибка сборки, а не «кривая проверка».

```json
{
  "status": "done",
  "reason": null,
  "steps": [
    {
      "id": "s1",
      "url": "http://localhost:3000/bookings",
      "action": "открыл форму, отправил запрос дважды",
      "observed": "вторая запись не создана, показан toast «уже создано»",
      "console_errors": [],
      "failed_requests": [],
      "cache_headers": { "cache-control": "no-store" }
    }
  ]
}
```

| Поле                      | Тип и правила                                                                             |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| `status`                  | `done` — проверка выполнена; `not_run` — не выполнена (обязательно с причиной)            |
| `reason`                  | `null` или строка; при `not_run` — почему (см. ниже)                                      |
| `steps[]`                 | массив шагов; обязателен при любом `status` (при `not_run` — пустой массив)               |
| `steps[].id`              | `s1`, `s2`, … — `^s[1-9]\d*$`; на этот id ссылаются как `qa:<id>` в `review`/`evaluation` |
| `steps[].url`             | непустая строка — адрес, на котором выполнялся шаг                                        |
| `steps[].action`          | непустая строка — что именно сделали                                                      |
| `steps[].observed`        | строка (может быть пустой) — что увидели; наблюдение, а не оценка «работает»              |
| `steps[].console_errors`  | массив — записи ошибок консоли как есть                                                   |
| `steps[].failed_requests` | массив — упавшие запросы (URL, код, метод) как есть                                       |
| `steps[].cache_headers`   | `null`, объект или строка — заголовки кэша, если проверялись                              |

### `status: not_run`

`not_run` — не ошибка сама по себе: браузер может быть недоступен (нет MCP, нет стенда), и честный
`not_run` лучше выдуманного `done`. Требования:

- `reason` заполнен причиной, понятной человеку (`mcp_unavailable`, `no_dev_server`, …);
- `steps` — пустой массив: шагов не было, значит и id нет;
- `cycle-decide` превратит это в `unverified[]` и попробует добор (`ACQUIRE_EVIDENCE`), а не
  «проглотит» отсутствие проверки.

```json
{ "status": "not_run", "reason": "mcp_unavailable", "steps": [] }
```

## Ссылки `qa:<id>`

Ревьюер и оценщик ссылаются на шаг так: `qa:s1`. Разрешение ссылки (`resolveRef`,
`scripts/lib/cycle/refs.mjs`):

- шаг с таким `id` есть в `qa-web.json` этой итерации — ссылка разрешается;
- файла нет, шага нет, `status = not_run` — ссылка не разрешается, и `cycle-decide` считает её
  неразрешённой (`unresolved_refs`), а находка без разрешаемой ссылки понижается по правилам §5.6.

Поэтому `id` шагов стабильны: они входят в `evidence/qa-web.json` и в таблицу критериев PR
(`cycle-pr-body` печатает свидетельство `qa:<id>` как есть).

## ПДн и секреты

`qa-web.json` — артефакт цикла, но при сборке пакета свидетельств (`cycle-evidence packet`) его
содержимое проходит `redactQa`: e-mail → `[email]`, телефоны → `[phone]`, заголовки
`authorization`/`cookie` и строки соединения с паролем → `[secret]`. Сырой файл в каталоге цикла
остаётся как есть, поэтому:

- в `observed` не переносим тела ответов с пользовательскими данными;
- вместо токена в `cache_headers` пишем `[secret]`, если он туда попал;
- скриншоты с ПДн в репозиторий не кладём.

Правило проекта — `AGENTS.md` §«Секреты не печатаем»; здесь оно конкретизировано для QA.

## Кто что пишет

| Кто                        | Что делает с файлом                                                      |
| -------------------------- | ------------------------------------------------------------------------ |
| супервизор (этап `QA_WEB`) | пишет `qa-web.json` по сценарию из `AGENTS.md` проекта                   |
| `cycle-evidence packet`    | копирует в `evidence/qa-web.json` с маскированием (`redactQa`)           |
| `cycle-decide`             | читает: `not_run` → `unverified` + `acquire`; разрешает ссылки `qa:<id>` |
| `cycle-pr-body`            | печатает `qa:<id>` как свидетельство критерия                            |
| `validate.mjs`             | проверяет схему; битый файл — ошибка, а не «нет проверки»                |

Автоматики, которая запускает браузер, в ядре нет: сценарий и инструмент (MCP, Playwright, ручная
проверка) — свойство проекта. Ядро отвечает только за формат фактов и за то, чтобы отсутствие
проверки было видно в решении.
