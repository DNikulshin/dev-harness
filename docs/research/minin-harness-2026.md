# Harness как инженерная среда: разбор внешнего доклада

  1:02:54, `rutube.ru/video/0bce9b857fa99a8e2a494ba93f804685`.

## 1. Тезис доклада

Узкое место переехало с написания кода на его **проверку**: модель генерирует изменения быстрее, чем
организация успевает понять, нужны ли они. Ответ — не более умная модель, а инженерная среда вокруг
неё:

> harness — управляющая инженерная среда вокруг модели, которая превращает вероятностный интеллект в
> повторяемого программного исполнителя (00:26:34).

Отсюда роль: AI-инженер проектирует контекст, память, инструменты, точки остановки и проверки
(00:53:23–00:55:50), а не пишет логику руками. Классические компетенции (архитектура, БД, права,
безопасность) не отменяются — они становятся условием, чтобы harness вообще собрался.

## 2. Слои harness по источнику

Доклад раскладывает среду на слои; у каждого свой вопрос и своя точка отказа.

| Слой                                         | Вопрос, на который отвечает         | Как это выглядит у нас                                                                                                                               |
| -------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Контекст / RAG (00:33–00:34)                 | что агент **знает**                 | `docs/` + `local-rag` (правило `docs/rag.md`), норматив `protocol → orchestrator → orchestrator-core`                                                |
| Tools / MCP (00:35–00:38)                    | что агент **может делать**          | `gh` CLI, гейты как исполняемые команды, MCP-серверы; в ядре — только вызовы из конфига                                                              |
| Memory / state (00:38–00:40)                 | что агент **помнит** между сессиями | `state.json` цикла (единственный писатель — `cycle-state`), `plan.<n>.md`, `evaluation.<n>.md`; **между задачами памяти нет**                        |
| Тесты агента, не продукта (00:40–00:42)      | правильно ли агент **работал**      | `evals/` (сиды, пред-регистрация, скоринг), `cycle-decide` правила 0–5; агентских смоук-тестов «агент понял задачу и не пропустил шаг» как гейта нет |
| Observability / «agentability» (00:42–00:44) | **где** именно сломалось            | `driver.jsonl` + `driver.mismatch` (маршрутизация кодом), `manifest.<n>.json`, `metrics.json`, `cycle-report`                                        |
| Guardrails (00:43–00:45)                     | что агенту **запрещено**            | лимиты диффа/байтов/логов/стоимости в конфиге, `redact`, `secrets_scan`, `check-harness`; песочницы/контейнера нет                                   |

Петля, которую источник называет «архитектурой harness» (00:45:21): намерение → спецификация →
контекст → действие инструментами → автоматическая проверка → трейс → решение человека → запись в
память. Это почти дословно наш цикл `plan → code → gates → review → evaluate → decide`; отличие в
том, что у источника память — постоянный слой, у нас — каталог цикла.

## 3. Долг по проверке (verification debt)

Источник вводит «долг по проверке» / «долг по ревью» (00:21:57–00:25:10): изменения создаются
быстро, а валидируются медленно, и именно валидация становится ценностью, а не само решение. Схему
«наивный ИИ» (требования → модель → огромный дифф → человек разбирается) он противопоставляет схеме
со спецификацией, контекстом и автоматической проверкой до человека.

У нас это уже нормативно: `docs/orchestrator.md:519` (verification debt, ADR
[0009](../adr/0009-context-metrics.md)), ADR [0010](../adr/0010-verification-tax.md) — «налог на
проверку» как измеряемая величина, `docs/orchestrator-core.md` §5 (evidence, `unverified[]`,
`downgraded[]`). Ценность источника здесь не в термине, а в независимом подтверждении, что наш выбор
«факт — прогон, а не текст» — не локальная причуда.

## 4. Уровни зрелости проекта

По источнику (00:50:57–00:53:23, **утверждение источника, первоисточник не проверялся**) некая
«Stanford AI engineering»-классификация ставится внешним агентом, который заходит в репозиторий и
смотрит промпты, субагентов, воркфлоу:

1. нет AI в проекте — пишем руками;
2. ad-hoc промптинг;
3. промпты версионируются в репозитории, есть правила, команда переиспользует;
4. агентские процессы: типовая задача → вызвал нужного агента;
5. оркестрация: множество агентов под общим оркестратором.

Уровень «5» источник объявляет моментом появления роли AI-инженера. К таблице стоит относиться как к
чужой шкале самооценки: у нас нет ни её первоисточника, ни проверки, что уровни вообще упорядочены
так, как заявлено.

## 5. Что из этого применимо к нам (наблюдения, не решения)

- **Слой «тесты агента» у нас есть, но не как гейт.** `evals/` меряет качество цикла на сидах, а не
  «не пропустил ли агент шаг» на конкретной задаче. Кандидат: смоук-цикл с проверкой
  последовательности стадий и реакции на смену модели — сейчас ни `driver.mismatch`, ни `state.json`
  не утверждают, что порядок шагов обязателен.
- **Guardrails у нас — числа, а не структура.** Лимиты и `secrets_scan` ограничивают объём и утечки,
  но нет изоляции: агент работает в том же рабочем дереве, что и человек (сегодня — буквально
  параллельно с другой сессией).
- **Памяти между задачами нет.** `state.json` живёт в каталоге цикла; решения, принятые в одной
  задаче, переносятся только через `docs/` и issues. Источник считает межсессионную память отдельным
  слоем — у нас эту роль фактически играет документация.
- **Наблюдаемость у нас измеряется, а не декларируется:** `driver.jsonl` и `context`-блок
  `metrics.json` ближе к «observability» источника, чем его же «agentability» — у нас нет трейса
  «какой слой отказал» (контекст / вызов модели / инструмент / проверка).

## 6. Что не брать из источника

- **Маркетинговый блок** (00:47:12–00:50:31): практикум, «агентская OS», ссылки на платную программу
  — к нашему ядру отношения не имеет.
- **Искажения автосубтитров:** «опус 4 и 8», «Кими 3», «Квн 32000000000 параметров» — это, очевидно,
  искажённые названия моделей и размеров (речь о 32B-классе). Любые числа из транскрипта требуют
  первоисточника.
- **Ссылки на исследования без проверки.** Доклад ссылается на «Эффект harness» и METR, но по
  первоисточникам мы их не сверяли: в наших документах такие утверждения без прогона не появляются.
- **Аргумент «пузырь лопнет — технологии останутся»** (00:56:38–00:59:31) — рассуждение о рынке, не
  о нашей архитектуре; проверяемых следствий для ядра не даёт.
