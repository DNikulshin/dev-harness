# Методики и тулинг: karpathy, evolution-design, pi

> **Исследование, не норматив.** Нормативные документы — `docs/protocol.md`,
> `docs/orchestrator-core.md`, `docs/orchestrator.md`. Здесь собрано, какие инженерные приёмы
> используют соседние проекты и где в рантайме pi может жить то, что у нас сегодня живёт только в
> тексте промптов. Детали изученных продуктов меняются, даты — на момент чтения источников.

## 1. Karpathy: минимализм и петля экспериментов

### 1.1 `autoresearch` — автономный цикл «правка → замер → принять/отбросить»

Устройство: три значимых файла, у каждого свой владелец.

| Файл         | Кто правит  | Смысл                                              |
| ------------ | ----------- | -------------------------------------------------- |
| `prepare.py` | никто       | данные, константы, утилиты оценки — «земля»        |
| `train.py`   | **агент**   | единственный файл, который агенту разрешено менять |
| `program.md` | **человек** | инструкции агенту («super lightweight skill»)      |

Плюс жёсткие рамки: прогон всегда ровно 5 минут, метрика одна (`val_bpb`, не зависит от размера
словаря), результат прогона — «улучшилось / нет», журнал экспериментов остаётся. За ночь — около ста
прогонов.

Переносимые приёмы:

1. **Разделение «что правит агент» и «что правит человек» на уровне файлов**, а не просьбами. У нас
   это `AGENTS.md` «не трогать» + заморозка критериев (#22) — но границы неявные: список «не
   трогать» — проза.
2. **Фиксированный бюджет вместо «до результата».** Сравнимость появляется из ограничения, а не из
   дисциплины. У нас есть бюджет стоимости (`maxCycleCostRub`), но нет бюджета времени на проход:
   два диффа разного размера сравниваются по-разному.
3. **Одна метрика для экспериментов.** Когда метрик три (полнота, ложные блокировки, ₽), решение
   «стало лучше?» размывается. Для A/B нужна одна главная величина, остальные — ограничения.
4. **Журнал прогонов как первый класс.** `autoresearch` держит лог экспериментов; у нас это
   `metrics.json` + `cycle-report`, и они появились позже решения, а не до него.

### 1.2 `llm-council` — перекрёстная оценка с анонимизацией

Три стадии: независимые ответы → каждый участник ранжирует чужие ответы **с скрытыми именами** →
председатель сводит в один ответ.

Переносимые приёмы:

1. **Анонимизация судей** — участник не знает, чей ответ оценивает. Наш `evaluate` слеп к плану и
   отчёту кода, но не анонимизирован по источнику: он знает, что перед ним единственный кандидат.
2. **Отдельная роль агрегатора.** У нас агрегатор — код (`cycle-decide`), а не модель: строже.
3. **Ранжирование вместо бинарного вердикта** даёт калибровку между моделями — полезно для A/B
   моделей оценщика (сейчас сравнение идёт по «поймал/не поймал»).

### 1.3 `rendergit` и минимализм `nanochat` / `minbpe`

- `rendergit`: репозиторий → один статический артефакт с двумя видами — человеческим (подсветка,
  навигация) и «LLM view» (CXML для вставки в чат). Идея: **артефакт для модели собирается как
  единый документ**, а не как набор путей.
- `nanochat`, `minbpe`, `micrograd`: «один скрипт, ноль конфигов, но воспроизводимо» — минимализм
  как способ держать читаемость, а не как экономия.

Для нас: `evidence/` — это набор файлов, которые судья читает по отдельности. Пакет для судьи («один
markdown: критерии, дифф, гейты, QA») уменьшил бы шанс пропустить часть входа — как `rendergit` для
кода.

## 2. `evolution-design`: решения — источник, документы — проекция

Репозиторий, который решает ту же проблему, что и мы, но для документации: как не дать докам
разъехаться с принятыми решениями.

| Механизм               | Как устроено                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Лог решений            | `decisions/` с семействами `project/` (процесс), `methodology/` (смыслы), `tool/` (тулинг); нумерация внутри семейства, файл `NNNN-суть.md` |
| Связи                  | Поля `Отменяет` / `Дополняет`; обратные ссылки `Отменено` / `Дополнено` **пересобираются с нуля** из прямых полей                           |
| Кто пишет              | Лог пишет **только человек** — «ни черновиком, ни на подпись»; агент находит дыры и говорит о них                                           |
| Иммутабельность        | Иммутабелен **смысл**, а не форма: орфография и обратные ссылки чинятся молча, остальное — спрос                                            |
| Скилл `check-decision` | Ищет логические дыры, противоречия между решениями, неявные переопределения; форма — молча                                                  |
| Скилл `decisions-fold` | Решение → проекции (доки, README, скиллы) по разделу `## Порождает`; и обратное направление: ручная правка проекции — форма или смысл?      |
| Архитектурный линтер   | `edlint` (вдохновлён `steiger`): детерминированная проверка архитектуры, VFS для скорости                                                   |
| Прочее                 | Монорепо `@evod/core` + `edlint` + `@evod/kit`; релизы changesets; `.claude/skills` рядом с кодом                                           |

Почему это важно нам: у нас **уже был** этот класс дефекта — норматив ссылался на `docs/evals.md` и
`docs/qa-web.md`, которых не было; §18 против §17; «H2–H4» вместо H2. Ни один тест такого не ловит,
потому что проверяется не соответствие «решение ↔ норматив», а только внутренняя связность кода.

Переносимые приёмы:

1. **Лог решений как единственный источник нормативных изменений**, доки — проекция, дрейф ловится в
   обе стороны. Наш аналог — `docs/adr/` + `docs/local/provenance.md`, но они не связаны с
   нормативом и не проверяются.
2. **Скилл, который проверяет решения, не имеет права их менять.** У нас такого разделения нет:
   правки норматива делает тот же агент, что и код.
3. **«Если вариантов больше одного — спроси»** как явное правило для агента (у нас это только в
   `AGENTS.md` для владельца).
4. **Пересборка обратных ссылок из прямых** — устойчиво к пропущенным запускам. Наш аналог: список
   задач в roadmap (#23) и `docs/board.md`, которые не выводятся из issues автоматически (доска
   выводится, roadmap — нет).

## 3. pi: где enforcement может жить в рантайме

Сегодня наша обвязка живёт «сбоку»: CLI-скрипты + текст в `templates/.pi/prompts/cycle.md` + правила
в `AGENTS.md`. pi даёт точки, где то же можно делать кодом внутри рантайма.

### 3.1 Поверхности pi

| Поверхность                                       | Что даёт                                                                                        |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `tool_call` (событие)                             | **Блокирует** вызов или мутирует его аргументы до исполнения (`{ block: true, reason }`)        |
| `tool_result` (событие)                           | Патчит результат инструмента (можно добавить разметку/отказ в вывод)                            |
| `context` / `context_with_system`                 | Меняет сообщения/транскрипт перед запросом к модели — политика, а не просьба                    |
| `before_agent_start`, `turn_end`, `agent_settled` | Точки для детерминированных переходов и учёта                                                   |
| `pi.registerTool` / `registerCommand`             | Нативные инструменты и команды (`/cycle`) вместо вызова shell                                   |
| `pi.setActiveTools(names)`                        | Ограничение набора инструментов в рантайме — независимость стадии обеспечивает код, а не шаблон |
| Skills (`.pi/skills/`)                            | Методика, подгружаемая по требованию; пакуется в npm/git-пакет                                  |
| Pi Package (`pi` в `package.json`)                | Один пакет раздаёт extensions + skills + prompts + themes; `pi config` включает нужное          |
| SDK (`createAgentSession`)                        | Внутрипроцессное управление сессией: свои инструменты, модели, промпты — база для драйвера      |
| RPC (JSONL)                                       | То же из другого процесса/языка                                                                 |
| Codemode                                          | Скрипты с вызовами инструментов + не-LLM классификаторы (дешёвая разметка)                      |
| MCP (`registerMcpServer`)                         | Публикация наших операций как MCP-инструментов для других harness                               |

Ограничения, которые надо держать в голове:

- Extension исполняется в процессе pi с правами ОС — это доверенный код проекта (вопрос trust);
- `tool_call` блокирует вызовы инструментов, но не защищает от записи через `bash`; значит либо
  ограничивать bash, либо разбирать команды — честно называть остаточную дыру;
- скиллы подгружает модель, и она может не подгрузить: обязательные шаги нельзя оставлять на скилле;
- API pi не 1.0: события и поля меняются, у потребителя без pi CLI должен остаться рабочим.

### 3.2 Маппинг наших пробелов на поверхности pi

| Наш пробел (issue / документ)                        | Механизм pi                                                                            | Что меняется                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Нет `init`: шаблоны копируются руками                | Pi Package (`pi`-манифест, npm/git) + `pi config`                                      | распространение становится установкой зависимости, а не инструкцией |
| H3 «независимость» проверяется статически по шаблону | `setActiveTools` в SDK-драйвере: `plan` — read/grep/find/ls, `code` — +edit/write/bash | правило держится рантаймом, а не текстом файла агента               |
| #27 integrity: тесты/конфиг гейтов правятся молча    | `tool_call`: блок правки `protectedPaths` + факт попытки в `evidence/`                 | «controls the agent cannot edit» на уровне инструмента              |
| Гейты описаны командами в конфиге                    | `registerTool` + `pi.exec`; результат можно патчить в `tool_result`                    | гейт виден модели как инструмент, а не как абзац промпта            |
| Фаза 3: драйвер стадий вместо LLM-супервизора        | SDK/RPC: маршрутизация кодом, смена инструментов по стадиям                            | меньше зависимость от дисциплины модели                             |
| Методика живёт в промптах                            | Skills: `cycle-protocol`, `evidence-review`, аналог `decisions-fold`                   | методика версионируется и подгружается по требованию                |
| Наши операции доступны только как CLI                | MCP-адаптер (`registerMcpServer`)                                                      | интероп с другими harness, не ломая CLI                             |
| Дорогие суждения там, где хватит классификатора      | Codemode classify                                                                      | разметка `in_scope`/`preexisting` без отдельной LLM-стадии          |

## 4. Что это меняет в плане A → B → C

- **A. Ядро контроля.** Появляется более сильная точка приложения усилий: не «проверить шаблон
  агента», а «ограничить инструменты и заблокировать правку защищённых файлов в рантайме». Заморозка
  критериев (#22) и integrity (#27) остаются, но реализуются там, где обойти нельзя.
- **B. Потребитель.** «Нет `init`» превращается в «есть пакет»: одна зависимость + `pi config`
  вместо копирования `.pi/*`. Плюс версия шаблонов = версия пакета, миграции = changelog пакета.
- **C. Измерение.** Формат эксперимента из `autoresearch`: фиксированный бюджет, одна метрика,
  журнал «принято/отброшено». У нас для этого уже есть `metrics.json` и `cycle-report`, но нет
  правила «одна метрика главная».

## 5. Кандидаты задач (черновик)

| Задача                                                                           | Куда       | Размер |
| -------------------------------------------------------------------------------- | ---------- | ------ |

| pi-extension `harness-guard`: `tool_call` → `protectedPaths`, факт в `evidence/` | A (#27)    | m      |
| SDK-драйвер MVP на двух стадиях (REVIEW/EVALUATE) с `setActiveTools`             | A (фаза 3) | l      |
| Skills в `templates/.pi/skills/`: `cycle-protocol`, `evidence-review`            | A/B        | s      |
| MCP-адаптер `cycle-state`/`cycle-decide`                                         | B          | m      |
| Единый пакет для судьи: `evidence/` → один markdown (идея `rendergit`)           | A          | s      |
| Лог решений → норматив: ADR как источник, доки как проекция, проверка дрейфа     | A          | m      |
