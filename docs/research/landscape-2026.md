# Ландшафт 2026: кто решает ту же задачу и чем мы от них отличаемся

> **Это исследование, а не норматив.** Ни один пункт здесь не обязателен к исполнению: нормативные
> документы — `docs/protocol.md`, `docs/orchestrator-core.md`, `docs/orchestrator.md`. Документ
> нужен, чтобы дальний план опирался на факты поля, а не на память. Даты и цифры — на момент
> изучения источников (список в конце), продуктовая часть поля меняется быстро.

## 1. Задача в терминах поля

`dev-harness` — это **control plane вокруг недетерминированного исполнителя**: скрипты решают, что
делать дальше; модели дают суждения. В литературе 2026 года это называют «harness» и разделяют три
режима принуждения к дисциплине (Consort, §III):

| Режим                          | Чем держится                               | Кто может нарушить                 |
| ------------------------------ | ------------------------------------------ | ---------------------------------- |
| persuasion                     | промпт, правила, ред-флаги                 | сама модель                        |
| front-loaded structure         | сильная спека + доверенная сборка          | модель, как только началась сборка |
| controls the agent cannot edit | код-оркестратор, гейты, неизменяемые тесты | никто из исполнителей              |

Наше позиционирование по этой шкале: **третий режим для решений и артефактов, второй — для
управляющего цикла.** Гейты и `cycle-decide` — код, который агент не редактирует; но сам цикл ведёт
LLM-супервизор, а критерии приёмки пишет планировщик и они не заморожены. Это ровно те две щели,
которые поле считает главными (§5).

## 2. Кластеры поля

### A. Spec-driven фреймворки (spec-first → spec-as-source)

| Проект                     | Что даёт                                                                                                                                                                             | Принуждение                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| **GitHub Spec Kit**        | CLI-инициализатор + пайплайн `constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge`; расширения, пресеты, бандлы, каталоги, воркфлоу-оверлеи | фронт-лоад: спека и чек-листы сильные, тесты опциональны и не гейтятся, конституция — проза |
| **Kiro (AWS)**             | `requirements → design → tasks` + steering (memory bank) + **hooks**: события файлов/сессии запускают команды или промпты                                                            | хук — детерминированная точка, но внутри IDE и по событию, а не по решению цикла            |
| **OpenSpec**               | change-артефакты: `proposal`, `delta specs` (`ADDED`/`MODIFIED`/`REMOVED`), `design`, `tasks`; `openspec validate`, затем merge в живую спеку                                        | валидация артефактов схемой; сборка — на агенте                                             |
| **obra/superpowers**       | методология как auto-triggering skills: brainstorming-гейт, «Iron Law» test-first, субагенты, стадийное ревью                                                                        | persuasion: весь контроль — промпт, оркестрация тоже модель                                 |
| **BMAD-METHOD**            | персоны (analyst/PM/architect/…) + PRD и архитектура; появился `bmad-loop` — детерминированный оркестратор с code-enforced гейтами                                                   | смешанное: гейты по покрытию/качеству после эпика, TDD внутри цикла не принуждается         |
| **GSD (Git. Ship. Done.)** | фазы `discuss → plan → execute → verify → ship`, свежий контекст в субагентах, состояние в файлах                                                                                    | конвенции и хуки, не код-гарантии                                                           |
| **Tessl**                  | spec-as-source: код генерируется из spec, `// GENERATED FROM SPEC`                                                                                                                   | вендорская платформа, spec-anchored/spec-as-source                                          |

Общий вывод поля: **все согласны про «spec first», различаются тем, как принуждают после спеки.**
Критика (Böckeler, martinfowler.com) бьёт по фронт-лоаду: много markdown на ревью, «sledgehammer»
для мелких задач, ложное чувство контроля — агент игнорирует чек-листы. Это аргумент в нашу пользу:
у нас нет генерации пачки markdown-артефактов на каждую мелочь, есть один короткий `criteria.md` +
машинные JSON.

| Проект                                                                             | Что берём на заметку                                                                                                                                                                                                                      |

### C. Оценка и evals

| Проект                                                                                          | Что даёт                                                                                                                  |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Inspect AI (UK AISI + Meridian)**                                                             | фреймворк evals: 200+ готовых, sandboxing toolkit, LLM-graded scoring, GUI; агентные бенчмарки (SWE-bench, GAIA, Cybench) |
| **Terminal-Bench / aider polyglot / SWE-bench Verified / SWE-rebench / SWE-Bench Pro Verified** | измеряют «модель + harness» на задачах; SWE-rebench — против контаминации статического набора                             |
| **LLM-as-judge практика**                                                                       | судья ≠ генератор; кросс-судья и согласие судей; шум у порога; калибровка на людях                                        |

Наш `evals/` (8 сидов, полнота 0.86 при пороге 0.8, ложных блокировок 0,
`cycle-metrics`/`cycle-report`) — та же логика, но в масштабе одного проекта и без внешнего
сравнения. Поле считает публичный нейтральный инструмент условием доверия: Consort прямо планирует
отдать свой grader как framework-neutral артефакт именно потому, что «инструмент внутри системы под
тестом — не независимый».

## 4. Где мы сильны (и это стоит удерживать)

1. **Механизм и политика разведены конфигом.** Ни один SDD-фреймворк этого не делает: у них процесс
   зашит в шаблоны и команды, у нас гейты/лимиты/пути — данные.
2. **Решение — машинный артефакт.** `cycle-decide` пишет `decision.<n>.json`; супервизору запрещено
   менять `action`. Это буквально «controls the agent cannot edit» на уровне, где конкуренты
   оставляют суждение модели.
3. **Слепой оценщик.** `evidence/` без плана и отчёта кода + проверяемые правила независимости
   семейств (H2–H4) — не текст в `AGENTS.md`, а проверка с кодом выхода.
4. **Стоимость и бюджет внутри цикла.** `usage.json` → `metrics.json` → порог `maxCycleCostRub`; у
   конкурентов стоимость считается постфактум в observability-платформе, а не как гейт.
5. **Нет сервисной зависимости.** ESM + plain Node, артефакты на диске: цикл переживает падение
   процесса без Temporal и без БД.

## 6. Три возможных дальних плана

### Сценарий A. «Ядро контроля» (enforcement-first)

Довести третий режим до конца: заморозка критериев, защита тестов и гейтов от ослабления,
детерминированная передача стадий (фаза 3), затем — нейтральный evals-инструмент.

- Плюсы: ровно то, чем мы отличаемся от SDD-фреймворков; каждая задача закрывает реальный failure
  mode.
- Минусы: не видно снаружи; второй проект подключается по-прежнему руками.
- Когда выбирать: если dev-harness живёт для собственных проектов и главное — доверие к результату.

### Сценарий B. «Потребитель» (adoption-first)

`harness init` (шаблоны + конфиг + проверка раскладки), версионирование шаблонов и миграции,
README/quickstart, закрытие висячих ссылок, статический HTML-отчёт по циклам.

- Плюсы: подключение нового проекта — минута; документация перестаёт врать; отчёт виден владельцу.
- Минусы: не улучшает качество решений; `init` — новый класс поверхности (нужны тесты, миграции).
- Когда выбирать: если проектов-потребителей будет больше двух или появится кто-то внешний.

### Сценарий C. «Измерение» (evals-first)

Сделать evals-слой настоящим: расширить набор сидов, пред-регистрировать метрики (полнота, ложные
блокировки, уникальные находки оценщика, стоимость на цикл), опубликовать нейтральный scorer,
прогнать A/B моделей как эксперименты.

- Плюсы: единственный способ проверить, окупаются ли `evaluate` и `review`; аргумент для внешних.
- Минусы: расход токенов на сами прогоны; результат — «данные», а не «функция».
- Когда выбирать: если под вопросом сам состав цикла (например, нужен ли отдельный оценщик).

**Рекомендация.** Порядок A → (дешёвые пункты B) → C, с «фаза 3» внутри A: сначала заморозка
критериев и защита тестов (дёшево, закрывает главный failure mode), затем перевод маршрутизации в
код по уже накопленным фактам, параллельно — висячие ссылки и `init` как гигиена, evals — когда
появится гипотеза, которую надо проверить, а не «на всякий случай».
