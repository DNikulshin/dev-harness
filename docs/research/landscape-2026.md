# Ландшафт 2026: кто решает ту же задачу и чем мы от них отличаемся

> **Это исследование, а не норматив.** Ни один пункт здесь не обязателен к исполнению: нормативные
> документы — `docs/protocol.md`, `docs/orchestrator-core.md`, `docs/orchestrator.md`. Документ
> нужен, чтобы дальний план опирался на факты поля, а не на память. Даты и цифры — на момент
> изучения источников (список в конце), продуктовая часть поля меняется быстро.

## 1. Задача в терминах поля

`dev-harness` — это **control plane вокруг недетерминированного исполнителя**: скрипты решают, что
делать дальше; модели дают суждения. В литературе 2026 года это называют «harness» и разделяют три
режима принуждения к дисциплине (Consort, §III):

| Режим                          | Чем держится                               | Кто может нарушить                 |
| ------------------------------ | ------------------------------------------ | ---------------------------------- |
| persuasion                     | промпт, правила, ред-флаги                 | сама модель                        |
| front-loaded structure         | сильная спека + доверенная сборка          | модель, как только началась сборка |
| controls the agent cannot edit | код-оркестратор, гейты, неизменяемые тесты | никто из исполнителей              |

Наше позиционирование по этой шкале: **третий режим для решений, второй — для управляющего цикла и
для части артефактов.** `cycle-decide` пишет решение как машинный артефакт, но `decision.<n>.json`
лежит в рабочем дереве, а `apply-decision` принимает изменённое содержимое как новое решение: запрет
«не менять `action`» живёт в промпте, то есть это persuasion. Гейты берут команды из
`.pi/harness.config.json`, который агент с правом записи может изменить. Сам цикл ведёт
LLM-супервизор. Критерии приёмки при этом **не пишет ни планировщик, ни исполнитель**: их дословно
извлекает из issue детерминированный `cycle-evidence`, а `plan` — read-only.

Сверка с репозиторием (2026-11-20) сдвинула картину в двух местах. Цель итерации закреплена кодом:
`state.criteria_sha256` — дайджест канонической формы `evidence/criteria.md`, расхождение на
следующей итерации останавливает `cycle-decide` (`criteria_drift`); правка тестов или конфига гейтов
code-агентом помечается в `evidence` и входит в правило решения. Остающийся разрыв — маршрутизация:
этапы передаёт LLM-супервизор, а не скрипт.

Общий вывод по перечисленным проектам: **первенство спецификации признают все, различаются они тем,
как принуждают после спеки.** Это вывод по семи продуктам, описанным в основном через вторичные
источники (см. §8), а не консенсус поля целиком. Критика (Böckeler, martinfowler.com) бьёт по
фронт-лоаду: много markdown на ревью, «sledgehammer» для мелких задач, ложное чувство контроля —
агент игнорирует чек-листы. Нас это касается частично: у нас меньше шагов, чем в конвейере Spec Kit,
но не «один файл» — на итерацию пишутся `plan.<n>.md`, `code-report.<n>.md`, `review.<n>.md`,
`evaluation.<n>.md`, при доработке — `rework-brief.<n>.md`, плюс `evidence/issue.md` и
`evidence/criteria.md`. Отличие в другом: это отчёты разных ролей, а не вход сборки, и решения по
ним принимает код.

## 4. Где мы сильны (и это стоит удерживать)

1. **Механизм и политика разведены конфигом.** Из перечисленных SDD-фреймворков политику в конфиг
   выносит только OpenSpec (частично), у Spec Kit, Kiro, BMAD и GSD процесс зашит в шаблоны и
   команды; у нас гейты, лимиты и пути — данные.
2. **Решение — машинный артефакт.** `cycle-decide` пишет `decision.<n>.json`, и действие берётся из
   него, а не из текста супервизора. Оговорка: файл лежит в рабочем дереве, и запрет менять `action`
   — правило промпта (`templates/.pi/prompts/cycle.md`, I4), то есть persuasion, а не физическое
   ограничение. Integrity-проверка закрыта (#27, #36): правка тестов и конфига гейтов помечается в
   `evidence`, а правило решения её учитывает.
3. **Слепой оценщик.** `evidence/` без плана и отчёта кода + правило независимости семейств,
   проверяемое кодом: H2 запрещает общее семейство для `code`↔`review` и
   `evaluate`∈{`code`,`review`}. Важно: ребро `evaluate`↔`plan` H2 намеренно не проверяет — именно
   там висит принятый риск §18 `docs/orchestrator.md`. H3/H4 — это права инструментов и префикс
   провайдера, не независимость.
4. **Стоимость и бюджет внутри цикла.** Порог `maxCycleCostRub` проверяет `cycle-decide` (правило 7)
   по накопленному `usage.json` и снапшоту цен — до того, как появится `metrics.json`;
   `metrics.json` пишется позже и служит отчётом. Такой гейт по стоимости мы не встретили у
   перечисленных продуктов, но специально не проверяли — это утверждение об отсутствии, а не
   измерение.
5. **Нет сервисной зависимости.** ESM + plain Node, артефакты на диске: цикл переживает падение
   процесса без Temporal и без БД.
6. **Цель итерации закреплена кодом.** `state.criteria_sha256` — дайджест канонической формы
   `evidence/criteria.md`; на следующей итерации расхождение — отказ `cycle-decide`
   (`criteria_drift`), а не «живая спека» автора. Такого enforcement у перечисленных продуктов мы не
   встретили: у большинства спека остаётся файлом, который можно править по ходу.

## 6. Три возможных дальних плана

### Сценарий A. «Ядро контроля» (enforcement-first)

Довести третий режим до конца: заморозка критериев, защита тестов и гейтов от ослабления,
детерминированная передача стадий (фаза 3), затем — нейтральный evals-инструмент.

- Плюсы: ровно то, чем мы отличаемся от SDD-фреймворков; каждая задача закрывает реальный failure
  mode.
- Минусы: не видно снаружи; второй проект подключается по-прежнему руками.
- Когда выбирать: если dev-harness живёт для собственных проектов и главное — доверие к результату.

### Сценарий B. «Потребитель» (adoption-first)

`harness init` (шаблоны + конфиг + проверка раскладки), версионирование шаблонов и миграции,
README/quickstart, закрытие висячих ссылок, статический HTML-отчёт по циклам.

- Плюсы: подключение нового проекта — минута; документация перестаёт врать; отчёт виден владельцу.
- Минусы: не улучшает качество решений; `init` — новый класс поверхности (нужны тесты, миграции).
- Когда выбирать: если проектов-потребителей будет больше двух или появится кто-то внешний.

### Сценарий C. «Измерение» (evals-first)

Сделать evals-слой настоящим: расширить набор сидов, пред-регистрировать метрики (полнота, ложные
блокировки, уникальные находки оценщика, стоимость на цикл), опубликовать нейтральный scorer,
прогнать A/B моделей как эксперименты.

- Плюсы: единственный способ проверить, окупаются ли `evaluate` и `review`; аргумент для внешних.
- Минусы: расход токенов на сами прогоны; результат — «данные», а не «функция».
- Когда выбирать: если под вопросом сам состав цикла (например, нужен ли отдельный оценщик).

**Рекомендация.** Порядок A → (дешёвые пункты B) → C, с «фаза 3» внутри A. Фаза A закрыта целиком:
заморозка критериев (#22), защита тестов и конфига гейтов (#27), ребро `evaluate`↔`plan` (#31),
связка `qa-web` (#30), конфликт записи `state.json` (#33) и детерминированный драйвер стадий вместо
LLM-супервизора (#47) — все на `main`. Дешёвые пункты B тоже закрыты: висячие ссылки (#21),
`harness init` (#41) и статический HTML-отчёт (#45) — это была гигиена, а не улучшение решений.
Обязательного следующего шага по плану нет: остался сценарий C, и он начинается не с работы, а с
гипотезы, которую надо проверить (агрегация повторов сидов #32 — только инструмент, а не результат).
Evals — когда такая гипотеза появится, а не «на всякий случай».

## 8. Источники

1. Consort — _Introducing Consort: A Spec-First Agent Framework for Enforced, Test-Driven
   Development on Live Database Branches_, arXiv:2609.09671 (таксономия режимов принуждения,
   immutable tests, honest-green, контекстный бюджет, сравнительная матрица пяти фреймворков).
2. GitHub Spec Kit — репозиторий и README (пайплайн, расширения/пресеты/бандлы/каталоги).
3. Birgitta Böckeler, _Understanding spec-driven development: Kiro, spec-kit, and Tessl_,
   martinfowler.com, 2025 (spec-first/spec-anchored/spec-as-source, критика фронт-лоада).
4. Kiro docs — _Hooks_ (событийные автоматизации, `PreTaskExecution`/`PostTaskExecution`).
5. OpenSpec docs — change-артефакты, delta specs, `openspec validate`, схемы и merge в живую спеку.

   таблица Consort §II-D/V, написанная автором одного из сравниваемых продуктов. Собственные README
   этих проектов не читались.
7. LangChain, _Checkpointers_ (`docs.langchain.com/oss/python/langgraph/checkpointers`): при replay
   «nodes after the checkpoint re-execute, including any LLM calls, API requests, or interrupts —
   which are always re-triggered during replay» — то есть восстановление из чекпоинта повторно
   тратит токены. Плюс обзор durable execution для агентов (Temporal, Restate, Inngest, DBOS).
8. Inspect AI (UK AISI, `inspect.aisi.org.uk`) — фреймворк evals, sandboxing toolkit; Inspect Evals
   (SWE-bench, GAIA). Инструменты оценки терминала — `tbench.ai` (Terminal-Bench), Aider LLM
   Leaderboards (`aider.chat/docs/leaderboards`, polyglot на 225 задачах). Названия приводятся как
   ориентир, сами наборы мы не прогоняли.
9. SWE-bench Verified / SWE-rebench / SWE-Bench Pro Verified — контаминация статических наборов и
   свежие задачи (SWE-rebench собирает задачи из активных репозиториев непрерывно).
10. Сравнение четырёх ревью-инструментов на 146 PR за три недели (dev.to, 2026-05-12: CodeRabbit,
    Sentry Seer, Greptile, Cursor BugBot) — маленькая выборка одной команды, не рецензируемое
    исследование; оттуда доля ложных срабатываний CodeRabbit 2.3%. Aikido, _Top Greptile
