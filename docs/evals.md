# Замеры оркестратора: сиды, прогоны, скор

Документ описывает **обвязку** замеров из `docs/orchestrator.md` §15: как устроен набор сидов, как
собрать прогон, как получить ответы этапов и как считается отчёт. Политика (зачем мерить, какие
пороги считать допустимыми) — в §15 `docs/orchestrator.md`; здесь — механика скриптов.

Коды выхода везде одинаковы по смыслу: `0` — успех; `2` — ошибка использования или данных (битый
JSON, нет нужного файла, неизвестный флаг). У `evals-score` есть ещё `1` — отчёт записан, но пороги
нарушены: это факт о данных, а не сбой инструмента.

## Что измеряется и что нет

Измеряется поведение **суждений**: ловит ли `review` и `evaluate` заранее заложенный дефект, не
блокируют ли они чистый дифф, окупает ли себя каждая стадия. Поэтому в прогоне участвуют только
`review` и `evaluate` (`SCORED_STAGES`); `cycle-decide` в обвязке не вызывается и
`decision.<n>.json` не пишется — статусы и объединение по сиду считает сам `evals-score`. `plan` и
`code` в замерах не участвуют: их качество проверяется боем, а не синтетикой.

Не измеряется: скорость моделей, качество кода, стоимость `plan`/`code` на реальных задачах (её даёт
`cycle-metrics` по боевым циклам).

## Набор сидов

Каталог — `evals/orchestrator/seeds/*.json` (`evals.seedsDir` в конфиге). Один файл — один сид на
фиксированном синтетическом дереве. Ниже — форма (значения сокращены; полный пример —
`evals/orchestrator/seeds/E5.json`):

```json
{
  "id": "E5",
  "title": "…что за дефект…",
  "why": "…на какое правило опирается ожидание…",
  "expect": { "kind": "defect", "severity": "BLOCKER", "file": "path/to/file.ts", "line": 11 },
  "issue": { "title": "…", "body": "…" },
  "criteria": ["…", "…"],
  "base": { "path/to/file.ts": "…исходное содержимое…" },
  "after": { "path/to/file.ts": "…содержимое после правки…" },
  "deleted": []
}
```

| Поле                         | Смысл                                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                         | `E<номер>`; порядок в таблице §15                                                                                                                             |
| `title`, `why`               | что за дефект и на какое правило он опирается                                                                                                                 |
| `expect.kind`                | `defect` — дефект должен быть найден; `clean` — контрольный сид, блокеров быть не должно                                                                      |
| `expect.severity`            | минимальная серьёзность попадания: `BLOCKER` или `MAJOR`; засчитывается «не ниже» (ожидание `MAJOR` принимает `BLOCKER`)                                      |
| `expect.severities`          | точный набор допустимых серьёзностей: `BLOCKER`, `MAJOR`, `MINOR`, `FOLLOW-UP`; совпадение по вхождению, без «не ниже»; с `severity` одновременно не задаётся |
| `expect.file`, `expect.line` | где ожидается находка; строка сравнивается с допуском `±5` (`LINE_TOLERANCE`)                                                                                 |
| `issue`, `criteria`          | вход этапов: текст issue и готовые критерии приёмки                                                                                                           |
| `base`, `after`, `deleted`   | синтетическое дерево: базовое состояние коммитится, `after` — рабочее дерево (дифф)                                                                           |

Фактическое состояние набора: **8 сидов** — `E1`–`E6`, `E9`, `E10`. Из таблицы §15 не заведены `E7`
(там ожидается падение гейта, а не суждение модели), `E8` и `E11` — открытые задачи, а не забытые
файлы: `evals-score` про сид без файла не догадывается.

`AGENTS.md` репозитория копируется в базовый коммит: правила проекта действуют и на синтетическом
дереве, а в дифф не попадают.

Каталоги прогонов и `report.json`/`report.md` лежат в `<artifacts>/evals/`, который в `.gitignore`:
в репозитории их нет. Поэтому числа «полнота 0.86» из `docs/orchestrator.md` §17 воспроизводятся
только повторным прогоном набора, а не открытием файла.

## Пайплайн прогона

```
evals-pack    → каталог прогона (.pi/artifacts/evals/<date>-<seed>-<config>/)
субагенты     → review.md / evaluate.md (пишет супервизор: у них нет прав на запись)
evals-collect → ответ и токены из транскрипта: <stage>.md + usage.json
evals-score   → report.json + report.md по всем каталогам прогонов
evals-cost    → справочная таблица ₽ (файлов не пишет)
```

### 1. `evals-pack` — каталог прогона

```bash
node scripts/evals-pack.mjs --seed E5 --config current [--now ISO] [--force]
```

Флаги: `--seed` (обязателен), `--config` (имя кандидата из `evals/candidates.json` либо `current` —
по умолчанию; при ином значении `evals-pack` ищет кандидата и падает с кодом 2, если его нет),
`--out` (явный каталог прогона), `--now` (фиксированное время — прогон воспроизводим), `--force`
(**удаляет** существующий каталог целиком, вместе с уже собранными `review.md`, `evaluate.md` и
`usage.json`), `--root`. Пишет только внутрь `<artifacts>/evals/` и отказывается работать по чужому
пути.

Содержимое каталога:

| Путь                   | Что там                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `tree/`                | синтетический git-репозиторий: база закоммичена, правка сида — в рабочем дереве                                                  |
| `evidence/diff.patch`  | `git diff` этого дерева с новыми файлами (`--intent-to-add`, как в `cycle-evidence`)                                             |
| `evidence/issue.md`    | текст issue сида                                                                                                                 |
| `evidence/criteria.md` | критерии приёмки сида: `- C1 <формулировка>` без двоеточия (так пишет `evals-pack`; формат ядра `- C1: …` здесь не используется) |
| `evidence/gates.json`  | пустой список гейтов: на синтетическом дереве они не запускаются, и это сказано явно                                             |
| `meta.json`            | `seed`, `config`, `models`, `stages`, `created_at`, `expect`                                                                     |

### 2. Прогон этапов

Субагенту `review`/`evaluate` отдают `evidence/` каталога прогона (как в настоящем цикле), ответ
целиком сохраняет супервизор в `review.md` / `evaluate.md` того же каталога. Конфигурация моделей —
только `.pi/agents/*.md`: матрица `evals/candidates.json` **не** меняет агентов, это дельты для
расчёта стоимости и для ручного применения в эксперименте.

Правило §15 — минимум **3 повтора** на сид: модели недетерминированы, один прогон ничего не значит.
Повтор — это тот же `--config` и **другой** `--out` (прямой подкаталог `<artifacts>/evals/`:
`findRuns` рекурсию не делает). `--config` — имя кандидата, а не свободный ярлык повтора.

Ограничение, которое надо знать: `evals-score` повторы **не агрегирует**. Статус пишется по сиду и
стадии (`seedEntry.stages[stage] = status`), поэтому следующий прогон того же сида затирает
предыдущий, и полнота считается по последнему наблюдению, а не «по большинству», как требует §15.
Агрегация — отдельная задача; пока повторы нужны, чтобы увидеть разброс глазами.

### 3. `evals-collect` — ответ и токены из транскрипта

```bash
node scripts/evals-collect.mjs --run <каталог прогона> --stage review \
  --transcript <id>_review_transcript.jsonl
```

Зачем отдельный шаг: pi сохраняет ответ субагента дважды, и копии не равноценны —
`<id>_<agent>_output.md` обрезается по размеру, а полный текст последнего сообщения лежит в
`<id>_<agent>_transcript.jsonl`. Скоринг обязан видеть полный ответ, иначе валидный блок ```json
теряется и этап выглядит сломанным.

Скрипт делает ровно два дела:

1. вытаскивает текст последнего ответа ассистента и пишет `<run>/<stage>.md`;
2. дописывает в `<run>/usage.json` фактические токены этого прогона (по стадии).

Без `usage.json` стоимость в отчёте — `null` («не измеряли»), а не выдуманная из профиля: профиль —
приближение, отчёт обязан показывать факт.

### 4. `evals-score` — отчёт и пороги

```bash
node scripts/evals-score.mjs [--runs DIR] [--seeds DIR] [--prices FILE] \
  [--completeness 0.8] [--fp-max 0.2]
```

Читает `meta.json` каждого каталога, ответы `<stage>.md`, `usage.json` и снапшот цен; пишет
`report.json` и `report.md` в каталог прогонов и печатает таблицу в stdout.

Пороги по умолчанию (`DEFAULT_THRESHOLDS`): полнота ≥ `0.8`, доля ложных блокировок ≤ `0.2`. Это
**допущения** §15, а не измеренная истина: вердикт `ok` значит «данные не противоречат порогам», а
`below_threshold` — повод посмотреть прогоны, а не приговор модели.

Порог проверяется только по вычисленной величине: если все ответы дефектных сидов оказались
`invalid`, полнота = `null`, и конфигурация получает `ok` — «проверять было нечего», а не «порог
выдержан». Каталог без ответов попадает в отчёт как пропущенный; если ответов нет нигде,
`evals-score` завершается кодом 2 и `report.json` не пишет.

### 5. `evals-cost` — сколько это стоит

```bash
node scripts/evals-cost.mjs [--json] [--model <id>]... [--prices FILE] [--profiles FILE] [--candidates FILE]
```

Считает ₽ за прогон каждой стадии и за «цикл» (по одному прогону `plan`, `code`, `review`,
`evaluate`) по снапшоту цен и профилям нагрузки. Дополнительные итерации `code` в «цикл» не входят:
они зависят от исхода цикла, а не от цен, и добавляются в уме как `N × code`. `--model` добавляет
строку «все стадии на этой модели» — так видно цену кандидата, которого ещё нет в матрице. Файлов не
пишет: это справочный расчёт.

## Скоринг: статусы и агрегаты

Каждый прогон стадии получает статус (`RUN_STATUSES` в `scripts/lib/evals/score.mjs`):

| Статус           | Что значит                                                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hit`            | дефект сида найден: тот же файл и `\|Δline\| ≤ 5`, серьёзность из ожидаемых. У ревью позиция берётся из `file`/`line`, но находки с `in_scope !== true` или `preexisting === true` в матчинг не идут; у оценщика позиция — строки `path:line` из `evidence[]` |
| `miss`           | дефект не найден или назван другой файл/строка                                                                                                                                                                                                                |
| `clean`          | на чистом сиде блокеров нет — как и ожидалось                                                                                                                                                                                                                 |
| `false_positive` | на чистом сиде выставлен `BLOCKER`/`MAJOR` — ложная блокировка                                                                                                                                                                                                |
| `invalid`        | в ответе нет блока ```json или не проходит схема — прогон не засчитывается                                                                                                                                                                                    |

По сиду считается объединение стадий (`union`): `hit`, если сид поймала хотя бы одна стадия; дальше
агрегаты по конфигурации:

- **полнота** = `hits / (hits + misses)` — доля пойманных дефектных сидов;
- **ложные блокировки** = `false_positives / clean_runs` — доля чистых сидов, заблокированных зря;
- **эксклюзивные хиты** (`exclusive.review` / `exclusive.evaluate`) — сиды, которые поймала ровно
  одна стадия. Пустая колонка у этапа — сигнал §15: этап не окупает стоимость, его надо убрать или
  сменить модель;
- **средняя стоимость** (`avg_cost_rub`) — по прогонам, где `usage.json` есть; иначе `null`.

`invalid` не считается попаданием и не считается промахом по вине модели: сначала чинится обвязка.

## Настройки: цены, профили, кандидаты

| Файл                    | Что это                                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `evals/prices.json`     | снапшот каталога провайдера: ₽ за 1M токенов (`input`, `cache_read`, `cache_write`, `output`), `_meta.source` и `fetched_at`                           |
| `evals/profiles.json`   | профиль нагрузки стадии: средние токены и число вызовов на прогон; `_meta.basis` — на каких прогонах измерено                                          |
| `evals/candidates.json` | матрица экспериментов: кандидат = дельта к текущим моделям агентов (`plan`/`code`/`review`/`evaluate`); `_meta` прямо говорит, что это не конфигурация |

Три файла обновляются **вручную** и с датой в `_meta`: снапшот цен без даты невозможно
интерпретировать, а профиль без указания базиса выглядит как факт, хотя это среднее. Автоматического
обновления нет намеренно: молчаливое «освежение» цен меняло бы исторические отчёты.

## Что остаётся за кадром

- Пороги §15 — допущения; калибруются по прогонам, а не подгоняются под удобный результат.
- Синтетика не заменяет бой: вывод «этап полезен» подтверждается `cycle-report` по `metrics.json`
  боевых циклов (`docs/orchestrator.md` §11).
- Набор не защищён от контаминации: сиды короткие и лежат в репозитории, поэтому сравнение моделей
  по ним — внутренняя калибровка, а не публичный бенчмарк.
