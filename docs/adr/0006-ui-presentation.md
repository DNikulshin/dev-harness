# 0006. UI — презентация артефактов, а не управление циклом

- **Статус:** принято
- **Дата:** 2026-11-20
- **Контекст:** после ADR [0004](./0004-core-runtime-adapters.md) (ядро — свой пакет, рантайм —
  чужой) и ADR [0005](./0005-layout-profile.md) (раскладка — данные) возник вопрос про
  пользовательский интерфейс. Проверка исследования по UI дала три факта. Первый: **своего UI у ядра
  нет** — ни сервера, ни фреймворка; единственный UI-артефакт — `cycle-report --html` (#45): одна
  самодостаточная страница, стили внутри, без JS и без сети, модель отчёта общая с markdown, вывод
  побайтно детерминирован. `docs/vision.md:34` прямо исключает «Web UI для просмотра циклов» из
  v0.1. Второй: предлагавшийся как «готовая база» Web UI из монорепо расширений — не приложение с
  API, а **расширение рантайма**: его точка входа импортирует `ExtensionAPI` и читает каталог
  агента, то есть вне рантайма пакет не живёт. Переиспользование означало бы «Harness-вьюхи внутри
  Pi» — то есть привязку продукта к одному рантайму, что ADR 0004 запрещает. Третий: класс «рабочая
  среда» (сессии, стриминг, терминал, worktrees, Mission Control) уже занят несколькими зрелыми
  приложениями вокруг того же рантайма; конкуренция там означает строить второй рантайм, а не ядро
  жизненного цикла.

## Решение

**(а) UI показывает, а не решает.** Интерфейс отображает артефакты цикла (`state.json`,
`gates.<n>.json`, `evidence/`, `decision.<n>.json`, `escalation.json`, `metrics.json`) и разрешённые
команды запускает **человек** через CLI. UI не владеет состоянием, не инициирует переходы, не
пересчитывает вердикты и не может обойти гейт: единственный источник истины — файлы, которые пишет
ядро.

**(б) Ядро не получает UI-инфраструктуру.** Ни сервера, ни JS, ни состояния представления в
`scripts/`. Сегодня это уже так, и правило фиксируется, чтобы следующая итерация не начиналась с «а
давайте прямо в ядре поднимем сервер».

**(в) Порядок — A → B.** Вариант **A** (сейчас): довести `cycle-report --html` до наблюдаемого
минимума — ответ на вопрос «почему цикл встал»: решение и его причины, эскалация, критерии
(met/unmet/unverified), незавершённые циклы отдельным списком вместо счётчика, различие `not_run` и
`fail`. Требования сохраняются: один файл, без JS и сети, побайтный детерминизм, ничего не пишется
на диск самим скриптом. Вариант **B** (когда понадобится): read-only просмотрщик артефактов
отдельным пакетом — список циклов, состояние, evidence, диффы. Команд управления в нём нет:
«открыть», «отфильтровать», «показать причину» — да; «перевести стадию», «запустить гейт» — нет, это
CLI. Вариант **C** (рабочая среда с сессиями и стримингом) **не развивается**: это другой продукт, и
его уже делают приложения вокруг рантайма.

**(г) Критерии перехода.** A → B: артефактов больше, чем удобно читать статической страницей (не
один цикл, а история; появились диффы и большие `evidence/`). B → C не рассматривается до появления
второго рантайма и собственного API: без них workbench — это UI поверх одного исполнителя.

## Последствия

- **Положительные:** UI нельзя «соврать» — он рисует уже зафиксированные файлы; нет дублирования
  состояния (класс дефектов «UI показывает одно, ядро другое» отсутствует по построению); ноль
  зависимостей и ноль поверхности атаки; вопрос «оставить или переписать UI» закрыт: переписывать
  нечего.
- **Отрицательные / цена:** нет интерактивности сверх запуска команд человеком; история циклов
  читается файлами, а не интерфейсом; при росте числа циклов статическая страница станет тесной —
  это и есть триггер B.
- **Что становится запрещено:** поднимать сервер и держать состояние в ядре; переносить UI из чужого
  расширения как основу продукта; инициировать переходы стадий из UI; вводить JS в отчёт
  (детерминизм и «файл открывается с диска» дороже удобства).

## Рассмотренные альтернативы

| Вариант                                                          | Плюсы                                  | Минусы                                                                                                                                                 |
| ---------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Взять Web UI расширения как основу                               | готовые сессии, стриминг, git-панели   | это расширение рантайма, не приложение с API: продукт привязывается к одному исполнителю (против ADR 0004); поддержка — синхронизация с чужим монорепо |
| Свой workbench (сессии, стриминг, терминал)                      | полный контроль UX                     | конкуренция с уже зрелыми приложениями; месяцы работы; ядро остаётся без наблюдаемости всё это время                                                   |
| Только markdown-отчёт (как до #45)                               | ноль работы                            | причину остановки приходится собирать `grep`-ом по JSON — именно эта боль и породила вопрос про UI                                                     |
| Готовые desktop-приложения вокруг рантайма (нативные и Electron) | готовый UX, worktrees, Mission Control | это не наш продукт: мы не управляем их дорожной картой и не встраиваем в них Harness; годятся как источник UX-паттернов                                |

## Проверка

- Тест: `--html` не содержит `<script`, внешних `src`/`href` и одинаков на двух запусках (уже есть
  для отчёта; расширяется на новые блоки).
- Тест: отчёт различает `not_run`/`fail`/`insufficient_data` и перечисляет незавершённые циклы, а не
  только считает их.
- Ревью-правило: в `scripts/` нет сервера и фронтенд-зависимостей — проверяется тем же способом, что
  и литералы раскладки (ADR 0005): глазомер не считается.
