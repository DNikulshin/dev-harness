# 0004. Ядро — свой пакет, рантайм — чужой, адаптеры — отдельные

- **Статус:** принято
- **Дата:** 2026-11-20
- **Контекст:** продукт должен ставиться и работать у внешнего пользователя, а не только в
  проектах-потребителях одного владельца. Три факта задают рамку. Первый: runtime цикла (модели,
  инструменты, сессии, субагенты) — не наш; сейчас это `pi`, и он останется не единственным. Второй:
  площадка расширений `pi-coding-agent-forge` — чужой аккаунт (`Firstp1ck`), все пакеты в ней
  публикуются в scope `@firstpick`, движка внутри нет; локальный форк — рабочая копия с
  обязательством синхронизации, а не канал поставки. Третий: ядро уже поставляется только по
  git-ссылке при `private: true`, а соглашения `pi` зашиты в проверку раскладки (`check-harness`
  H1–H6 читает `.pi/agents/*`, `.pi/settings.json`, `.pi/prompts/cycle.md`), и роль супервизора
  играет главная сессия `pi` (`docs/orchestrator.md:35`). То есть зависимость от конкретного
  рантайма в ядре есть, но она не названа и не отделена.

## Решение

**(а) Ядро — самостоятельный публикуемый пакет.** Продукт для внешнего пользователя — установка из
реестра: `@dnikulshin/harness` в своём npm-scope, `private: true` снимается релизным PR, тег
`vX.Y.Z` — контракт версии. Git-ссылка остаётся способом для пилота и для правок до релиза, но не
единственным. Следствие: публичный API (`exports`, `bin`, схемы артефактов) становится обещанием
semver, а не «как получилось».

**(б) Runtime не форкаем и не пишем свой.** `pi` используется как есть, другие рантаймы добавляются
адаптерами. Свой оркестратор (свой вызов моделей, планировщик, sandbox, провайдеры) — не цель
проекта: он конкурирует с рантаймом, который уже есть, и уводит от единственного преимущества —
детерминированного ядра.

**(в) Адаптер — отдельный пакет в своём scope.** Адаптер знает API рантайма и ничего не знает о
внутренностях ядра: контракт — CLI и JSON-артефакты (`cycle-driver next`, `gates.<n>.json`,
`decision.<n>.json`, `state.json`). Адаптер `pi` публикуется в scope `@dnikulshin`, а не в чужом
`@firstpick`: вклад в чужой монорепо возможен как PR, но релизный контроль продукта остаётся своим.

**(г) Форк чужого монорепо — не часть поставки.** `pi-coding-agent-forge` остаётся источником
паттернов (готовые расширения, релизные пайплайны) и, при желании, каналом PR upstream. Продукт
через него не распространяется: иначе темп, scope публикации и решения о совместимости определяет
чужая площадка.

**(д) Зависимость ядра от раскладки рантайма называется «профиль раскладки».** Сейчас профиль один —
`pi`: `.pi/harness.config.json`, `.pi/agents/*` (frontmatter, H1–H6), `.pi/prompts/cycle.md`.
Правила H1–H6 остаются, но объявляются проверками профиля, а не ядра; всё, что знает про API
рантайма (hooks, сессии, вызовы моделей), живёт в адаптере. Профиль `generic` появляется вместе со
вторым адаптером, а не впрок: абстракция без второго потребителя — догадка.

## Последствия

- **Положительные:** продукт ставится одной командой и не требует чтения нормативa, чтобы начать;
  релиз и совместимость под своим контролем; второй рантайм добавляется пакетом, а не форком ядра;
  ядро не соревнуется с чужим монорепо за темп и приоритеты.
- **Отрицательные / цена:** нужны npm-scope, релизный пайплайн и дисциплина semver; пакетов
  становится два и более (ядро + адаптеры), их совместимость нужно объявлять; «профиль раскладки»
  добавляет слой между ядром и файлами проекта; чужие паттерны придётся переносить, а не
  наследовать.
- **Что становится запрещено:** форкать чужой harness как основу продукта; публиковать адаптер в
  чужом scope; импортировать из адаптера внутренности ядра (`scripts/lib/**`); добавлять в
  `scripts/` код, знающий API рантайма; заявлять «поставил и работает» до того, как внешний
  consumer-фикстур (#66) докажет контракт.

## Рассмотренные альтернативы

| Вариант                                                         | Плюсы                                                    | Минусы                                                                                                                                         |
| --------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Форк `pi-coding-agent-forge` как площадка продукта              | готовые релизы, экосистема расширений, один `pi install` | чужой upstream и scope; контроля над runtime нет; 13 тыс. файлов и 769 МБ в рабочем каталоге; каждое обновление — синхронизация с чужим темпом |
| Свой runtime/оркестратор                                        | полный контроль, независимость от `pi`                   | месяцы работы; дублирует сессии, инструменты, субагентов, ретраи; конкуренция с Loops/Flow/Sudarshan на их поле                                |
| Форк чужого harness (Flow, Sudarshan, Development Orchestrator) | быстрый старт, готовые механизмы                         | чужая архитектура и лицензии; выбрасывается уже написанное ядро и норматив; чужая дорожная карта                                               |
| Только git-зависимость, без реестра                             | ноль инфраструктуры, полный контроль версий              | не «поставил и работает»: потребитель обязан знать про теги, git-доступ и `pnpm add -D`                                                        |
| Писать адаптер сразу в чужом монорепо                           | один экосистемный вход, готовый пайплайн релиза          | чужая политика совместимости; ядро и адаптер расходятся по релизам; upstream зависит от вашего пакета без вашего контроля                      |

## Проверка

- Контракт адаптера проверяется #66: внешний consumer-фикстур обязан работать через CLI и `exports`,
  без импорта `scripts/lib/**`. Если для адаптера этого не хватает — плохой контракт, а не адаптер.
- Отсутствие Pi-кода в ядре и наличие профиля раскладки — будущая задача (issue на профиль); до неё
  долг зафиксирован здесь, чтобы H1–H6 не считались «нейтральными правилами ядра».
- Публикация в реестр — отдельная задача: `private: false`, релизный workflow, проверка `pnpm pack`
  составом (`LICENSE`, `templates/`, `types/`).
