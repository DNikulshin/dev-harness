# 0005. Профиль раскладки — данные в конфиге, а не ветка в коде

- **Статус:** принято
- **Дата:** 2026-11-20
- **Контекст:** ADR [0004](./0004-core-runtime-adapters.md) назвал долг: соглашения `.pi/` (агенты,
  настройки, промпт цикла, каталог артефактов) лежат в ядре и выглядят как «правила ядра», хотя это
  раскладка одного рантайма. Перед вторым адаптером нужно решить, чем раскладка является и где она
  живёт. Проверка кода показала, что механизм уже есть и он данными: `config.paths` содержит
  `artifactsDir`, `agentsDir`, `settings`, `cyclePrompt`, `agentsMd`, а чтение идёт через них —
  `artifactsDir()` и `readHarness()` берут пути из конфига, а не из литералов. Долгом осталось
  другое: (1) расположение самого конфига зафиксировано константой
  `CONFIG_FILE { dir: '.pi', name: 'harness.config.json' }` (`scripts/lib/cycle/config.mjs:29`); (2)
  `check-harness` читает по конфигу, но **называет** пути литералами `.pi/...`
  (`scripts/check-harness.mjs:416,508,512,518,528`) и сортирует вывод по литералам в `FILE_ORDER`
  (`:139-146`) — при нестандартном профиле диагностика врёт, а порядок вывода перестаёт быть
  детерминированным; (3) `harness-init` ставит шаблоны по литеральному префиксу `.pi/`
  (`TEMPLATE_PREFIX`) и создаёт `.pi/harness.config.json`; (4) около тридцати сообщений об ошибках
  конфига начинаются с литерала `.pi/harness.config.json`.

## Решение

**(а) Раскладка — данные.** Профиль раскладки — это набор значений `paths` в
`.pi/harness.config.json`. Отдельного файла раскладки, поля `profile:` и ветвления по имени профиля
не вводится: второй профиль — другой набор путей (и, если понадобится, другой шаблон установки), а
не другая кодовая ветка. Абстракция без второго потребителя — догадка (ADR 0004, д).

**(б) Фиксирована ровно одна точка — где искать конфиг.** Она становится явной границей CLI:
`--config <file>` (и переменная окружения для тех же случаев), по умолчанию
`.pi/harness.config.json`. Всё остальное — из конфига. Логика «где конфиг» живёт в одном месте
(`lib/cycle/config.mjs`), а не повторяется в каждом `bin`.

**(в) H1–H6 — проверки профиля, а не ядра.** Они читают пути из конфига (уже так) и обязаны называть
в выводе **фактические** пути: диагностика, которая зовёт файл `.pi/agents/plan.md`, когда он лежит
в `harness/agents/plan.md`, хуже отсутствия диагностики. Порядок файлов в выводе тоже берётся из
профиля: иначе детерминизм вывода зависит от того, совпали ли пути с умолчаниями.

**(г) `harness-init` ставит по профилю.** Шаблоны копируются в каталог из `paths`, пример конфига
создаётся там, где конфиг ожидается. Литеральный `.pi/` остаётся только значением по умолчанию в
константах путей.

**(д) Правило проверяется механизмом.** Тест обходит `scripts/**` (кроме модуля умолчаний и тестов)
и падает, если в коде есть литерал `.pi/`. Иначе через месяц правило снова станет пожеланием:
сегодня таких литералов десятки, и именно поэтому долг незаметен.

**(е) Имя «профиль» появляется в документации тогда, когда появится второй набор умолчаний.**
Носитель при этом уже определён — `paths`; вводить имя раньше значит обещать больше, чем есть.

## Последствия

- **Положительные:** второй рантайм подключается изменением конфига и шаблонов, а не правкой
  `scripts/lib/**`; диагностика перестаёт врать при нестандартных путях; детерминизм вывода
  перестаёт зависеть от совпадения с умолчаниями; «где конфиг» — одна явная граница вместо
  константы, размазанной по сообщениям.
- **Отрицательные / цена:** правка `check-harness` (передать профиль в `analyzeHarness` и в
  `FILE_ORDER`), ~30 сообщений конфига, `harness-init`, плюс тест-grep; миграция потребителя не
  нужна — умолчания не меняются, но `harness-init` на нестандартном профиле начнёт вести себя иначе
  (это и есть исправление).
- **Что становится запрещено:** добавлять литерал `.pi/` в код (кроме констант умолчаний); ветвление
  «если профиль такой-то»; второй файл раскладки; вводить профиль `generic` до появления второго
  адаптера.

## Рассмотренные альтернативы

| Вариант                                                                  | Плюсы                            | Минусы                                                                                                                            |
| ------------------------------------------------------------------------ | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Отдельный файл раскладки (`.harness/layout.json`), конфиг ищется по нему | раскладка отделена от политики   | две точки bootstrap вместо одной: сначала найти раскладку, потом конфиг; новое состояние, которое надо валидировать и мигрировать |
| Поле `profile: "pi" \| "generic"` в конфиге                              | имя видно в одном месте          | ветвление ради одного потребителя; `generic` нечем проверить до второго адаптера                                                  |
| Ничего не менять, оставить литералы                                      | ноль работы                      | диагностика врёт на нестандартных путях; второй адаптер требует правок в `lib/**`, что ADR 0004 запрещает                         |
| Вынести раскладку вместе с H1–H6 в адаптер                               | ядро вообще не знает про рантайм | проверка раскладки перестаёт быть общей: у второго адаптера не будет проверки вообще, пока её не напишут заново                   |

## Проверка

- Тест-grep по `scripts/**`: литералов `.pi/` в коде нет, кроме констант умолчаний (появится вместе
  с правкой `check-harness`).
- Тест: профиль с нестандартными путями — нарушения H1/H5/H6 называют пути из конфига и идут в
  порядке профиля.
- Тест: `harness-init` на профиле с другим `agentsDir` кладёт шаблоны туда, а не в `.pi/`.
- `--config` проверяется тестом: конфиг вне `.pi/` находится, остальные пути берутся из него.

## Порядок работ

1. `check-harness`: пути в сообщениях и в `FILE_ORDER` из профиля (s).
2. `config.mjs`: сообщения об ошибках называют фактический путь конфига (s).
3. Граница CLI: `--config`/переменная окружения, один резолвер (m).
4. `harness-init`: установка по профилю (m).
5. После этого — адаптер второго рантайма (ADR 0004, в) без правок в `scripts/lib/**`.
