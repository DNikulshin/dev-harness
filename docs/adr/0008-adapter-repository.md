# 0008. Адаптер рантайма — отдельный репозиторий на контракте CLI

- **Статус:** принято
- **Дата:** 2026-11-20
- **Контекст:** ADR [0004](./0004-core-runtime-adapters.md) (в) решил, что адаптер рантайма —
  отдельный пакет в своём scope, и запретил ему импортировать внутренности ядра, но не сказал, **где
  этот пакет живёт**. Без ответа нельзя начинать #74: от него зависит, где лежат тесты контракта,
  как публикуются две версии и какой CI что проверяет. Факты, которые задают рамку:

  1. `@dnikulshin/harness` — самостоятельный публикуемый пакет с `bin` (17 команд), `exports` и
     схемами артефактов (`docs/release.md`); его устройство проверяет
     `tooling/check-package.test.mjs` (`pnpm pack` составом, `ERR_PACKAGE_PATH_NOT_EXPORTED` на
     закрытых путях).
  2. Адаптеру нужен **чужой API рантайма** (`ExtensionAPI` Pi: регистрация команд, инструменты,
     сессии). Это зависимость от версии рантайма — та самая, которую ADR 0004 (б) запретил вносить в
     ядро.
  3. Релизные темпы разные: ядро меняется по своим issue, адаптер — вслед за API рантайма. Общая
     история коммитов связала бы их релизы.
  4. Контракт уже наблюдаем без импортов: версия ядра (`package.json` установленного пакета и
     `harness.version` установки), `bin`-команды, JSON-артефакты (`state.json`, `gates.<n>.json`,
     `decision.<n>.json`).

## Решение

**(а) Адаптер живёт в отдельном репозитории** (`dnikulshin/pi-harness`) и публикуется как
`@dnikulshin/pi-harness` в своём scope. Монорепозиторий с pnpm-workspace в этом репозитории не
заводится: корневой пакет остаётся единственным, `pnpm pack` и проверки состава не меняются.

**(б) Контракт — только CLI и JSON.** Адаптер вызывает `bin` ядра (`cycle-driver next`,
`cycle-gates`, `cycle-state`, `cycle-report`, `harness-init`) и читает артефакты. Импорт
`scripts/lib/**` запрещён; `scripts/lib/cycle/config` — тоже, хотя он и в `exports`: адаптеру
достаточно флагов и файлов, а библиотечный шов существует для тестов ядра. Если чего-то не хватает,
это дефект контракта ядра (issue в этом репозитории), а не повод импортировать.

**(в) Совместимость объявляется адаптером, проверяется на старте.** Адаптер держит ядро в
`peerDependencies` с диапазоном, разрешает фактическую версию установленного пакета и сравнивает её
с диапазоном **до первого шага цикла**: несовпадение — один понятный отказ (код 1) с двумя версиями
в тексте, а не падение на середине стадии на изменившейся схеме артефакта. `harness.version` в
проекте — вторичный сигнал: он говорит, чем ставили шаблоны, а не чем работает цикл.

**(г) Тесты контракта остаются в ядре.** Внешний consumer-фикстур (#66) и проверки `exports`/`pack`
— здесь, в этом репозитории: ядро не может объявить себя совместимым, если проверка живёт в
потребителе. Адаптер в своём CI ставит опубликованное ядро из реестра и прогоняет фикстур; локальная
git-ссылка на ядро допустима только в разработке адаптера.

**(д) Граница с чужими расширениями записывается в README адаптера.** `pi-extension-workflows` и
подобные — произвольный повторяемый сценарий; `cycle` — протокол с замороженными критериями,
`evidence/` и машинным решением. Адаптер не пытается быть «workflows с гейтами»: в нём нет
пользовательских шагов, только стадии протокола.

## Последствия

- **Положительные:** ядро остаётся без зависимостей от рантайма (ADR 0004, б) и без Pi-кода; релизы
  адаптера и ядра независимы, совместимость — объявленный диапазон, а не «синхронно обновим оба»;
  тесты контракта по одну сторону (ядро), тесты рантайма — по другую; репозиторий ядра не получает
  769 МБ чужого монорепо и его API.
- **Отрицательные / цена:** два репозитория, две защиты ветки, два релизных пайплайна; правка
  контракта — два PR и порядок «сначала ядро, потом адаптер»; сквозная проверка «поставил и
  работает» требует, чтобы адаптер в CI ставил ядро **из реестра**, а не из git.
- **Что становится запрещено:** импортировать `scripts/lib/**` (в том числе через `exports`) из
  адаптера; держать Pi-код в `scripts/` и `tooling/`; публиковать адаптер в `@firstpick`; объявлять
  совместимость без проверки версии на старте; добавлять workspace-пакеты в этот репозиторий.

## Рассмотренные альтернативы

| Вариант                                          | Плюсы                                                     | Минусы                                                                                                                                                           |
| ------------------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отдельный репозиторий `pi-harness` (решение)     | независимые релизы и CI, ядро без зависимости от рантайма | два репозитория и два пайплайна; правка контракта — два PR                                                                                                       |
| Монорепозиторий: `packages/pi-*` здесь же        | один PR на контракт и адаптер, общий CI                   | корневой пакет становится workspace-корнем: меняются `pnpm pack`, `files`, проверки состава и релизный workflow; код ядра начинает разделять историю с чужим API |
| Один пакет: адаптер внутри `@dnikulshin/harness` | «поставил и работает» одним пакетом                       | в пакет ядра попадает зависимость от API рантайма (против ADR 0004, б) и второй релизный темп; потребитель без Pi тянет его код                                  |
| Адаптер в чужом монорепо `@firstpick`            | готовый пайплайн публикации и экосистема                  | чужая политика совместимости и scope; ядро и адаптер расходятся по релизам (ADR 0004, г)                                                                         |
| git-ссылка вместо реестра для адаптера           | ноль инфраструктуры                                       | «поставил и работает» превращается в «настрой git»; CI адаптера не может проверить опубликованную версию ядра                                                    |

## Проверка

- Адаптер: тест по импортам — ни одного пути `@dnikulshin/harness/scripts/**` и `scripts/lib/**` в
  исходниках; единственные обращения к ядру — `bin` и файлы артефактов.
- Адаптер: тест совместимости — с версией ядра вне `peerDependencies` цикл не начинается, код 1 и
  обе версии в тексте.
- Ядро: consumer-фикстур (#66) и `tooling/check-package.test.mjs` не ослабляются; правка контракта
  без них не проходит CI.
