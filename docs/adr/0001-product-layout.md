# 0001. Нейтральное ядро, профили и три класса артефактов

- **Статус:** принято
- **Дата:** 2026-11-19
- **Контекст:** dev-harness выносится из проекта-источника и должен стать продуктом, с которым любой
  full-stack проект получает уровень зрелого продукта «из коробки» — workflow, правила, доки,
  скиллы, реестр MCP, гейты, evals-контур, — не копируя ядро. Три ограничения задают рамку:
  - ядро не содержит названий проектов, пакетов, каталогов и моделей; политика приходит из
    `.pi/harness.config.json` и `AGENTS.md` потребителя;
  - opinionated-часть (архитектурные гейты, дизайн-практики, QA web, деплой) нужна потребителю, но в
    нейтральном ядре ей места нет;
  - поставляемые файлы (доки, хуки, шаблоны CI) живут в репозитории потребителя и без механизма
    сверки расходятся с пакетом — ровно та болезнь, из-за которой ядро выносилось.

## Решение

**(а) Ядро нейтральное, opinionated-часть — в профиле.** Профиль — это данные (`profile.json` в
пакете): дефолты конфига, список поставляемых доков, набор скиллов, набор гейтов, шаблоны workflow.
Профиль выбирается в `.pi/harness.config.json` (`"profile": "<id>"`), неизвестный или невалидный
профиль — ошибка конфига (код 2). Исполняемый код профиль не приносит: проверки (`check-harness`,
`check-arch` и подобные) живут в пакете и версионируются вместе с ним.

**(б) Каждый поставляемый артефакт принадлежит одному из трёх классов.**

| Класс     | Что                                                                                  | Правило                                                                       |
| --------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `bin`     | скрипты цикла, проверки, evals, хуки                                                 | не копируется: запускается из пакета; версия равна версии пакета              |
| `owned`   | `AGENTS.md`, `.pi/harness.config.json`, `.pi/agents/*.md` (модели), доки потребителя | генерируется один раз, дальше принадлежит проекту и не синхронизируется       |
| `managed` | нормативные доки, шаблоны промптов, CI-workflow, `gh-setup`                          | поставляется с манифестом; обновляется только при отсутствии локальных правок |

Класс файла задаётся манифестом профиля, а не устной договорённостью. Файл, которому нужны проектные
значения, не может быть `managed`: такие значения живут в конфиге и `AGENTS.md`.

**(в) Managed-файлы сопровождает манифест, расхождение ловит `harness sync --check`.** Манифест
(`harness.manifest.json`) фиксирует версию пакета и профиля, класс и хеш каждого файла.
`sync --check` печатает список расхождений и возвращает код 1; в CI он обязателен. `sync --write`
обновляет только файлы без локальных правок, изменённые — показывает и не трогает. Манифест
детерминирован: без дат, абсолютных путей и машинных данных.

**(г) Порядок внедрения — по зависимостям, а не одновременно:** хуки и проверки в `bin` → профиль →
манифест с классами → `sync --check` (затем `--write`). Каждый шаг выпускается отдельно и не ломает
предыдущий.

**(д) Потребителю видна одна команда.** Внутренняя таксономия классов наружу не выносится:
`harness sync --check` отвечает на вопрос «соответствует ли репозиторий профилю и версии пакета» и в
случае расхождения объясняет причину.

## Последствия

- Положительные: потребитель получает уровень зрелого продукта без сборки harness руками; дрейф
  поставляемых файлов перестаёт быть невидимым; ядро остаётся переносимым, потому что
  opinionated-часть вынесена в данные.
- Отрицательные / цена: нужен новый механизм (профиль, манифест, `sync`), плюс дисциплина
  раскладывать каждый новый файл по классам; двухстороннее слияние при `--write` откладывается, пока
  не понадобится.
- Что становится запрещено: класть проектные значения в `managed`-файлы; добавлять в профиль код;
  расширять ядро под конкретный проект вместо профиля; копировать `bin`-класс в репозиторий (копия
  ловится `sync --check`).

## Рассмотренные альтернативы

| Вариант                                          | Плюсы                                | Минусы                                                                               |
| ------------------------------------------------ | ------------------------------------ | ------------------------------------------------------------------------------------ |
| Всё в пакет, ничего не копируется                | нулевой дрейф                        | `AGENTS.md` и доки потребителя обязаны быть в его репозитории: их читает агент и RAG |
| Копирование «как в README» без манифеста         | дешево                               | дрейф неизбежен и невидим; это и была болезнь проекта-источника                      |
| Opinionated-гейты прямо в ядро                   | проще для одного проекта             | ядро знает проект — теряется переносимость и правило «никаких проектных строк»       |
| Профиль как отдельный npm-пакет на каждый пресет | независимое версионирование пресетов | инфраструктура из нескольких пакетов раньше, чем появился второй потребитель         |
