# 0007. Окружение гейтов: наследование по умолчанию, allowlist по объявлению

- **Статус:** принято
- **Дата:** 2026-11-20
- **Контекст:** гейт — это `executable` + `args` из `.pi/harness.config.json`, то есть произвольный
  код с правами пользователя. Окружение он наследует целиком: `gateEnv()` возвращает
  `{...process.env, TURBO_FORCE: 'true'}` (`scripts/cycle-gates.mjs:322`), поэтому гейт видит токены
  CI, креды БД, ключи провайдеров и `HARNESS_*`. Вопрос из #65 звучал как «нужен ли allowlist», но
  ответ на него зависит не от желания, а от того, от какого сценария защищаемся:

  | Сценарий                                                 | Что помогает                                                                                      | Даёт ли allowlist                   |
  | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------- |
  | чужой PR меняет конфиг гейтов                            | ревью конфига; `integrity.protectedPaths` уже помечает правку конфига в `evidence/integrity.json` | частично: код всё равно исполняется |
  | скомпрометированный бинарь в цепочке поставки            | пиннинг, lockfile, `ignore-scripts`                                                               | частично                            |
  | секрет попал в лог или артефакт                          | маскирование при захвате (#63)                                                                    | да, сужает поверхность              |
  | CI с долгоживущими секретами (`NPM_TOKEN`, ключи деплоя) | отдельный job без секретов, короткоживущие токены                                                 | **да, это главный аргумент**        |

  Изоляции allowlist не даёт: гейт по-прежнему может прочитать `.env`, `~/.npmrc` и сходить в сеть.
  Он меняет только то, что лежит в памяти процесса без чтения файлов. Поэтому «secure by default»
  здесь означал бы ломку документированного сценария: `test_int` получает `DATABASE_URL` из
  окружения намеренно (`docs/orchestrator-core.md:423-424` — скрипт `.env*` не читает), а `turbo`,
  `pnpm` и `node` требуют десятков переменных. Чёрный список имён (`*_TOKEN`, `DATABASE_URL`) ломает
  то же самое и создаёт ложное чувство защиты: настоящий секрет может называться иначе.

## Решение

**(а) По умолчанию — как сейчас: полное наследование.** Гейт без объявленного окружения получает
`process.env` плюс `TURBO_FORCE=true`. Ничего не ломается, поведение документировано как доверие к
конфигу проекта.

**(б) Гейт может объявить окружение** — полем `env` в своей записи:

```json
{
  "id": "format_check",
  "executable": "pnpm",
  "args": ["exec", "prettier", "--check", "."],
  "env": { "allow": ["npm_config_cache", "npm_config_user_agent"], "set": { "CI": "1" } }
}
```

- `allow` — имена переменных, которые наследуются из окружения вызывающего процесса;
- `set` — литеральные значения (не секреты: конфиг лежит в репозитории и попадает в историю).
- Объявил `env` — наследование выключается: гейт получает **только** `allow` + `set` + служебные.

**(в) Служебные переменные передаются всегда.** `PATH`, `HOME`, `TMPDIR` и `TURBO_FORCE` — не
секреты, а условия запуска: без `PATH` не разрешается `executable`, без `HOME` ломаются кэши `pnpm`
и `npm`, без `TURBO_FORCE` гейт отдаёт результат из кэша turbo (§5.5). Секреты в этот список не
входят никогда.

**(г) Валидация строгая, как везде в конфиге.** Неизвестное подполе `env` (`inherit`, `except`),
не-массив в `allow`, пустое имя, дубль имени, не-строка в `set` — код 2 с понятным текстом. `env` у
встроенного гейта (`builtin`) — ошибка: встроенная проверка идёт в процессе и окружения не получает.

**(д) Ядро не решает, доверять ли конфигу.** Оно лишь даёт команде, отвечающей за CI, способ не
отдавать секреты гейтам, которым они не нужны. Утверждение «гейт = код, который вы согласились
запускать» остаётся в документации, и `README` уже говорит это про доверие к конфигу.

## Последствия

- **Положительные:** в CI можно запускать гейты без доступа к `NPM_TOKEN` и ключам деплоя, не ломая
  `test_int`; решение принимает потребитель, а не ядро; обратная совместимость полная (поле
  необязательное); схема проверяется механизмом, а не ревью.
- **Отрицательные / цена:** новый элемент строгой схемы и обещание semver; потребитель, объявивший
  `env`, узнаёт о нехватке переменной только по упавшему гейту (диагностика — лог гейта, где видно
  `ENOENT`/пустое значение); «secure by default» не достигается — нужна дисциплина в CI.
- **Что становится запрещено:** хранить в `set` секреты; делать наследование «умным» (чёрные списки
  имён, урезание по `CI=true` — неявность по окружению хуже явного поля); обещать изоляцию и sandbox
  (это рантайм, ADR 0004).

## Рассмотренные альтернативы

| Вариант                                                 | Плюсы                 | Минусы                                                                                                                                 |
| ------------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Оставить как есть, только документация                  | ноль работы           | поверхность секретов в CI не сужается вообще                                                                                           |
| Allowlist по умолчанию (наследования нет)               | «secure by default»   | ломает `test_int` (`DATABASE_URL`), `turbo`, `pnpm`, `node`; миграция всех потребителей при одном потребителе — догадка вместо решения |
| Чёрный список имён (`*_TOKEN`, `*_KEY`, `DATABASE_URL`) | дешево                | ломает документированный `test_int`; секрет с другим именем проходит; ложное чувство защиты                                            |
| Урезание env по признаку `CI=true`                      | без изменений конфига | магия по окружению: поведение зависит от того, где запущено, а не от конфига                                                           |
| Sandbox/контейнер для гейтов                            | настоящая изоляция    | это рантайм и отдельный продукт (ADR 0004); цена несопоставима с задачей                                                               |

## Проверка

- Тест: гейт с `env.allow` видит разрешённую переменную и **не** видит неразрешённую
  (секрет-маркер), служебные `PATH`/`HOME`/`TMPDIR` доступны, `TURBO_FORCE` = `true`.
- Тест: гейт без `env` наследует окружение как раньше (обратная совместимость).
- Тест: `env` у `builtin`-гейта и мусор в `env` дают код 2; дубль имени в `allow` — код 2.
- Документация: §5.5 называет правило, `README` — модель доверия (конфиг гейтов = исполняемый код).

## Порядок работ

1. Схема и исполнение: поле `env` в `parseGate`, `GATE_FIELDS`, `gateEnv` по конфигу, тесты, §5.5.
2. Документация модели доверия: `README` и §5.5 — что означает «гейт доверенный» и как этим
   пользоваться в CI.
3. Собачья еда: задать `env` в собственном `.pi/harness.config.json` — после 1 и 2, отдельной
   проверкой, что гейты этого репозитория не сломались.
