# Процесс разработки: ветки, issues, Kanban

Модель: trunk-based с короткоживущими ветками. `main` всегда рабочая: ядро и пакет не должны
ломаться на голове ветки, изменения попадают только через pull request. Работа идёт по issues,
статусы — метками (они же колонки доски).

## Роли

| Шаг                                     | Кто      |
| --------------------------------------- | -------- |
| Декомпозиция, issue, ветка, коммиты, PR | агент    |
| Правки по ревью в той же ветке          | агент    |
| Проверка и merge PR                     | владелец |
| Проверка корректности слияния по тегу   | агент    |

Агент не пушит в `main` и не мержит PR. Исключение — первичный bootstrap пустого репозитория, явно
согласованный с владельцем.

Правило проверяется механизмом, а не памятью: `.githooks/pre-commit` и `.githooks/pre-push`
отклоняют коммит и push в `main`/`master` (`tooling/git-guard.mjs`), подсказывая команду создания
ветки. Обход — `git commit --no-verify` / `git push --no-verify`, только осознанно.

## Доска

Колонки = метки статуса; GitHub Projects — их отражение (`docs/board.md`).

| Колонка     | Метка                |
| ----------- | -------------------- |
| Todo        | `status:todo`        |
| In progress | `status:in-progress` |
| Review      | `status:review`      |
| Blocked     | `status:blocked`     |

`status:review` и `status:in-progress` переключает workflow `board-labels.yml` по событиям PR:
открытие PR → `review`, черновик → `in-progress`, закрытие → метки снимаются. Issue закрывается
строкой `Closes #<номер>` в теле PR. Карточки и колонку `Status` двигает `board-sync.yml` — правила
и секрет `PROJECT_TOKEN` описаны в `docs/board.md`.

## Ветки

```
feat/<номер-issue>-<коротко>     новая функциональность
fix/<номер-issue>-<коротко>      исправление
chore/<номер-issue>-<коротко>    инфраструктура, зависимости, репозиторий
```

Пример: `chore/5-packaging`. Ветка живёт не дольше одной задачи; после merge удаляется автоматически
(`delete_branch_on_merge`).

Squash-merge не делает коммит ветки предком `main`, поэтому «ветка не влита» и «есть что пушить» —
не признак незавершённой работы. Состояние берётся фактом:

```bash
pnpm git:hygiene              # локальные ветки со смерженными PR + статус текущей
pnpm git:hygiene --prune      # удалить такие ветки (текущая не удаляется)
gh pr list --head <ветка>     # состояние PR ветки
gh issue view <номер>         # состояние задачи
```

`pre-push` отклоняет push ветки, чей PR уже `MERGED` (`tooling/branch-guard.mjs`), и подсказывает
команду очистки. GitHub недоступен — только предупреждение: проверка защищённых веток работает
офлайн.

**База ветки.** Второй `pre-push`-гейт (`tooling/base-guard.mjs`) сверяет ветку с `origin/main`:

| Состояние                                        | Что делает хук                                                             |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| ветка содержит `origin/main`                     | молчит                                                                     |
| отстаёт, конфликта нет                           | предупреждает: проверки запустятся, но перед мержем ветку стоит обновить   |
| отстаёт **и** слияние базы даёт конфликт         | **отклоняет** push с командой `git fetch origin && git rebase origin/main` |
| `origin/main` неизвестен (офлайн), sha не коммит | молчит: отказ по догадке хуже подсказки                                    |

Причина отказа, а не аккуратности: **GitHub не запускает проверки у PR с конфликтами**. Такой PR
приезжает молчаливым — `gh pr checks` отвечает «no checks reported», и это читается как «CI ещё
идёт». На практике это случилось дважды (#182, #188): ветка создавалась от устаревшего локального
`main`, и причина находилась только на странице конфликтов.

Конфликт определяется без сети: локальный `refs/remotes/origin/main` и
`git merge-tree --write-tree`. Если база устарела, ответственность за `git fetch` остаётся на
разработчике — хук об этом не врёт и не притворяется, что сверялся с сервером.

## Коммиты

Формат: `<type>(<scope>): <что сделано>`, где `type` — `feat|fix|chore|refactor|test|docs`, `scope`
— `core|board|package|evals|ci|docs|infra`.

```
fix(core): лимиты из конфига проекта, а не из кода
feat(board): сверка доски Projects с issues
chore(ci): проверки ядра на PR
```

Один коммит — одно логическое изменение. Сообщения по-русски, без «wip» в финале. Язык кода и
комментариев — как в репозитории (русские комментарии, английские идентификаторы).

## Pull request

- Заголовок = одна строка о сути; в теле — `Closes #N`, «что сделано», «как проверять», чек-лист из
  шаблона.
- Объём: одна задача. Если дифф разрастается — дробить на PR.
- Merge — squash: в `main` попадает один коммит, история линейная. Merge commit и rebase отключены
  на уровне репозитория.
- PR не мержится, пока не зелёные обязательные проверки: `checks (ubuntu-latest)` и
  `checks (macos-latest)` — одна и та же матрица job `checks` (тесты, `typecheck`, актуальность
  `types/`, prettier, раскладка harness H1–H6); и `pr-references` (ссылка на issue, см. «Проверка
  ссылки на issue»). Список — `.github/workflows/ci.yml` и `pr-checks.yml`, правила ветки — в
  «Настройка». Имена проверок включают ОС: матрица и `REQUIRED_CHECKS` меняются вместе, иначе
  required check не появится и merge встанет.
- **Ссылка на issue обязательна:** в теле PR должна быть строка `Closes #<номер>`. GitHub закрывает
  issue ею в момент мержа, и только после этого доска переводит карточку в `Done`.
- Правила действуют и для владельца: `enforce_admins: true` — прямой push в `main` через UI/API/CLI
  отклоняется. Временное снятие защиты — осознанное действие владельца.

## Проверка ссылки на issue

Механизм: workflow `pr-checks.yml` (job `pr-references`) запускает `tooling/pr-reference.mjs` на
`pull_request` (opened / edited / reopened / synchronize / ready_for_review). Нет ссылки — джоба
падает с аннотацией `::error::` прямо в интерфейсе PR.

**Зачем, если есть правило.** GitHub связывает issue в момент мержа по ключевому слову в теле PR.
Тело, собранное из шаблона (`Closes #` без номера) или из сообщения коммита, ссылки не содержит: PR
влит, issue открыт, доска в прежней колонке. Так произошло дважды — #5 и #15: оба раза issue
закрывали руками, и доска на это время расходилась с репозиторием.

**Что засчитывается** (регистр не важен, двоеточие допустимо, ссылок может быть несколько):

```
Closes #12
closes #12
Closes: #12
Fixes #7
Resolves #3
```

**Что не засчитывается:**

- подсказка шаблона `Closes #<номер>` и любое упоминание внутри HTML-комментария `<!-- … -->`;
- примеры внутри блоков кода (` ``` ` или `~~~`);
- строки в обратных кавычках: `` `Closes #4` ``. GitHub ключевое слово внутри inline-code не
  распознаёт, поэтому проверка, которая его засчитывала бы, зеленела бы ровно там, где issue
  останется открытым (так и вышло с #4 в репозитории адаптера).

Иначе шаблон, в котором формат ссылки объяснён примером, проходил бы проверку, ничего не закрывая —
то есть механизм молчал бы ровно в том случае, ради которого сделан.

**Сообщения коммитов тоже закрывают issue (#181).** GitHub сканирует closing-слово не только в теле
PR, но и в сообщениях коммитов, причём **разметка там не защищает**: бэктики и блок кода ничего не
экранируют. Поэтому пример закрывающего слова с номером в тексте коммита закрывает чужой issue при
мерже — так и вышло: номер из примера в коммите совпал с открытым issue адаптера.

Проверка это ловит: `pr-reference.mjs` читает сообщения коммитов диапазона `base..head`
(`PR_BASE_SHA`/`PR_HEAD_SHA`, `git log --format=%B%x00`) и падает, если в них есть номер, которого
тело PR не закрывает. Избыточность допустима: коммит вправе повторить номер из тела.

**Правило для автора.** В тексте коммита закрывающее слово с номером целиком не приводим — пишем
словами («закрывающее слово», «closing-слово»), иначе пример работает как настоящая ссылка.

**Исключения.** PR от Dependabot не ссылаются на issue: у бота нет задачи в трекере, тело он не
правит. Для них джоба пропускается условием `github.actor != 'dependabot[bot]'`.

**Ручная проверка** (тело из gh, без CI):

```bash
PR_BODY="$(gh pr view 12 --json body --jq .body)" node tooling/pr-reference.mjs; echo "код: $?"
```

Коды: `0` — ссылки есть (в выводе номера issue); `2` — ссылки нет, тело пустое или коммит тянет
чужой номер. Тесты логики разбора — `tooling/pr-reference.test.mjs` (`node --test`): формы ключевых
слов, несколько ссылок, комментарии, блоки кода и inline-code, пустое тело, мусор вместо тела, чужие
номера в сообщениях коммитов и диапазон `base..head`.

## Проверка существования ссылок на issues

Ссылка на номер, которого нет, — то же самое, что ссылка на несуществующий документ: JSDoc и `docs/`
выглядят объяснёнными, а читатель уходит в пустоту. Механизмов два, они дополняют друг друга.

| Механизм                                               | Где работает         | Что ловит                                                             |
| ------------------------------------------------------ | -------------------- | --------------------------------------------------------------------- |
| `scripts/dead-issue-refs.test.mjs`                     | `pnpm check`, офлайн | возврат **уже известных** мёртвых номеров (снимок в самом тесте)      |
| `tooling/check-issue-refs.mjs` (workflow `issue-refs`) | CI: расписание и PR  | **новые** мёртвые номера и номера из чужих диапазонов — резолв в `gh` |

Сбор ссылок и исключения у обоих общие (`scripts/lib/issue-refs.mjs`): области — `scripts/*.mjs` и
`docs/*.md`; не считаются ссылками hex-цвета (`#6b7280`, а также целиком цифровые `#111827` —
поэтому номера длиннее пяти цифр не рассматриваются), адреса чужих трекеров (`owner/repo#233`),
номера в именах каталогов артефактов. Каталоги `docs/research/` и `docs/local/` не проверяются: это
исторические документы и журнал переноса.

```bash
pnpm issue-refs                    # проверка по сети (нужен gh и авторизация)
pnpm issue-refs:snapshot           # переписать снимок мёртвых номеров в тесте
node tooling/check-issue-refs.mjs --no-cache   # без кэша
```

Коды выхода: `0` — все номера существуют; `2` — есть мёртвые (список с адресами `файл:строка`); `3`
— `gh`, сеть или авторизация недоступны, часть номеров проверить не удалось. `3` — это не зелёный
прогон: «не знаю» и «всё хорошо» не должны выглядеть одинаково. Кэш резолва —
`.cache/issue-refs.json` (в `.gitignore`, срок жизни сутки), поэтому серия PR и суточный прогон не
упираются в rate limit; неизвестный результат не кэшируется никогда.

`issue-refs` не входит в обязательные проверки PR: `permissions` в `ci.yml` ограничены
`contents: read`, а сеть и rate limit не должны красить нормальный PR. По расписанию и по кнопке
(`workflow_dispatch`) job блокирующий, на PR — информационный (`continue-on-error`).

Снимок в тесте **генерируется**, а не правится руками: `pnpm issue-refs:snapshot` обходит те же
области, резолвит номера и переписывает `DEAD_REFS`, `SNAPSHOT_DATE` и `MAX_REF_AT_SNAPSHOT`
(`tooling/check-issue-refs.mjs`, тесты — `tooling/check-issue-refs.test.mjs`). Мёртвый номер не выше
максимального существующего — повод для ручной проверки, и такой снимок автоматически не пишется:
нумерация в трекере последовательная, значит это скорее ошибка резолва, чем факт.

## Инструмент GitHub

Только `gh` CLI: GitHub MCP не подключаем, UI — для чтения владельцем. Типовые команды:

```bash
gh issue view <номер> --json title,body,labels    # вход задачи
gh pr create --fill --body "... Closes #N"        # PR из ветки
gh pr checks <номер>                              # проверки PR
gh run view <id> --log-failed                     # упавший прогон
gh workflow run board-sync.yml                    # сверка доски вручную
```

Доска, секреты и переменные — через `gh` (`docs/board.md`): ручные правки в UI не воспроизводятся и
расходятся с репозиторием.

## Метки и релизы

Метки: `type:*` (`feature|bug|chore|spike`), `area:*`, `prio:p1..p3`, `size:s|m|l`,
`status:todo|in-progress|review|blocked`, `needs-owner` (нужно решение, а не код). Набор и цвета —
`tooling/gh-setup.mjs`.

Тег `v<major>.<minor>.<patch>` ставится на `main` после merge PR, закрывающего релизный issue.
Порядок: зелёный `checks` на `main` → `git tag -a vX.Y.Z` → `git push origin vX.Y.Z` → убедиться,
что CI прогнался на теге и workflow `Release` опубликовал версию. Версия в `package.json` и в теге
совпадают; пакет ставится из npm (`npx @dnikulshin/harness init`) или по git-ссылке с тегом
(`#vX.Y.Z`), поэтому тег — это контракт для потребителя.

`Release` (`.github/workflows/release.yml`) публикует **собранный архив**, а не репозиторий:
`pnpm check` → `pnpm pack` → проверка состава и версии (`tooling/check-package.mjs`) →
`npm publish --provenance` с секретом `NPM_TOKEN`. Состав архива проверяется до публикации, потому
что версию в npm нельзя перезаписать. Публичный API и правила версий — `docs/release.md`.

Ruleset `release-tags` запрещает удалять и перезаписывать теги `refs/tags/v*`: перезапись сделала бы
установку невоспроизводимой (под одним тегом разный код), удаление оставило бы потребителя с битой
ссылкой. Ошибочный тег лечится новым тегом, а не `push --force`. Что делать с уже опубликованной
версией — `deprecate` или `unpublish`, — [release.md](./release.md#отзыв-ошибочного-релиза).

## Spike: решение отдельно от кода

`type:spike` — задача, у которой результат не код, а решение. Формат один и тот же; образцы — #73 →
[ADR 0005](./adr/0005-layout-profile.md) и #83 → [ADR 0006](./adr/0006-ui-presentation.md).

1. **issue** с `type:spike`: что неизвестно, какое решение принимается, что считается готовым.
   Формулировка «исследовать вопрос» готовым не считается.
2. **Сверка фактов до решения.** Код, доки, внешние источники — в issue или ADR пишется, что
   подтвердилось, а что нет. Обзор без сверки — не основание: два внешних обзора в этой истории
   содержали утверждения о вещах, которых в репозитории нет.
3. **ADR** по [шаблону](./adr/0000-template.md): контекст, решение, последствия с ценой,
   альтернативы, проверка, порядок работ; строка в [реестре](./adr/README.md).
4. **Реализация — отдельными issues.** «Порядок работ» в ADR — ссылки на них, а не план внутри
   документа.
5. **PR только с документами**: код в тот же PR не едет — иначе решение и реализация рецензируются
   вместе, и спор о решении тонет в диффе.

Если решение можно проверить механизмом (тест, гейт, `check-harness`), ADR либо называет проверку,
либо явно говорит, что она появится вместе с реализацией: правило «проверяется глазомером» в
норматив не попадает.

## Настройка (один раз)

```bash
node tooling/gh-setup.mjs             # метки, режим merge, сканирование секретов
node tooling/gh-setup.mjs --protect   # дополнительно правила main и тегов
node tooling/gh-setup.mjs --dry-run   # показать вызовы, ничего не менять
```

Что выставляется (всё идемпотентно):

- **метки** — `type:*`, `area:*`, `status:*`, `prio:*`, `size:*`, `needs-owner`;
- **merge** — только squash, ветка после мержа удаляется;
- **секреты** — secret scanning и push protection, если ещё не включены: в репозитории фигурируют
  PAT доски, случайная копия токена в коммит — утечка;
- **`main`** — PR обязателен всем, включая владельца (`enforce_admins: true`), обязательные проверки
  `checks (ubuntu-latest)`, `checks (macos-latest)` и `pr-references` в актуальном состоянии с
  `main` (`strict: true`), линейная история, комментарии должны быть закрыты, force-push и удаление
  запрещены;
- **теги** — ruleset `release-tags`: `refs/tags/v*` нельзя удалить или перезаписать (см. «Метки и
  релизы»).

Проверка:

```bash
gh api repos/DNikulshin/dev-harness/branches/main/protection --jq '.enforce_admins.enabled'  # true
```

Защита ветки доступна только на публичном репозитории или платном плане: приватный репозиторий на
free-плане отвечает `403 Upgrade to GitHub Pro`. Если репозиторий снова станет приватным,
`--protect` перестанет работать, а правило «только PR» останется только в хуках.

## Definition of Done

- issue закрывается автоматически из PR (`Closes #N`);
- `pnpm check` зелёный (тесты, `typecheck`, prettier), `types/` актуальны; результат указан в PR;
- для задач, прошедших `/cycle`, обязательные гейты из `.pi/harness.config.json` зелёные; `not_run`
  без причины — блокер, `skipped` — нет;
- публичные точки входа пакета (`exports`, `bin`, `files`) не сломаны: изменение состава файлов
  проверяется установкой пакета (`pnpm pack` + установка в чистый проект);
- новая зависимость — только с обоснованием; ядро не знает проект (правила в `AGENTS.md`);
- вне скоупа замеченное — отдельным issue, а не «попутно»;
- локальная ветка после merge удалена (`pnpm git:hygiene --prune`), работа продолжается от
  обновлённого `main`.
